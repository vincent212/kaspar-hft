An Agent That Audits an HFT System Against Its Design Principles

An AI agent that measures a running Kaspar-HFT system against the four design principles of the CME measurement study, reports which it follows and which it violates, and turns the deployment dials until the measurements say no further change helps.

Vincent Mayeski, M2 Tech, Montreal

1. Why following the principles has to be measured

The previous article derived four design principles for market-data receivers from over a year of CME packet data, and a design flow that applies them. The principles are stated in terms of measured quantities: the publisher period of the feed, the per-packet service time of each stage under load, the cost of a thread hop, the number of messages a packet carries. None of these is a property of the source code. The same actor code, compiled once, follows the rules on one feed and violates them on another, or follows them at one message count per packet and violates them at a higher one.

Whether a deployed system follows the principles is therefore not a question a code review can answer. It is a measurement on the assembled system, running against the feed it will trade on, repeated after each change. That is work with a fixed procedure, fixed instruments and a fixed set of rules to compare against, and the procedure is long enough that it is skipped in practice. It is the kind of work a coding agent does well, provided the instruments exist and the rules are written down. In Kaspar-HFT both conditions hold. This article describes the audit agent: what it observes, which rules it checks, what it is allowed to change, and what it reports. As with the venue generator, the agent is a skill for Claude Code, stored in the repository and run inside a copy of it. The measurement tooling it uses is in the repository today; the skill that drives it is the design presented here.

2. The rules, stated as checks

The design flow of the measurement study is ten numbered steps. Written as checks that a running system either passes or fails, they reduce to the eight rules of Figure 1. The first seven are the paper's. The eighth comes from the probe's own documentation, which records the ways a latency number can be quoted wrongly, and treats each as a violation in its own right.

Three of the rules deserve comment, because they are the ones a human auditor gets wrong.

Rule 1 says the publisher period is measured, never assumed. On NQ it is about 7.5 μs and it did not move between quiet and volatile sessions, but that is a finding about one feed's publisher. The agent reads it from the low end of the gap distribution between consecutive packets, the first percentile, on every run. The mean gap is some three hundred times longer and a rule stated on it would never split anything.

Rule 2 compares a stage's service time with the period using the upper quantiles of service under load, not the median. A stage whose median is below the period and whose p99 is above it queues on exactly the packets that set the tail.

Rule 8 is the one the agent enforces on itself. Percentiles come from the per-message records, never from the maxima of 100 ms bins, which overstate the true p99 by a measured factor of about 1.7. Recovery windows are excluded, because during recovery live packets pile up and are later charged the whole drain as latency. The first minutes of a run are dropped. The probe must be compiled in, and the agent confirms it from the startup log, because without the build flag the run starts cleanly, records nothing, and leaves no error.

3. What the agent can observe

The agent does not instrument the system itself. It uses the latency probe that Kaspar-HFT already carries, and it is bound by what that probe measures. Figure 2 shows the market-data path and the three timestamps on it.

Two records come out of a run. Per packet, the read timestamp, the sequence number and the span, which is the number of messages the packet carries. Per message, the publish timestamp, the first leg, the mailbox depth at enqueue, and the message's index within its packet. From these the agent computes everything the rules need. The gaps between consecutive read timestamps give the publisher period. The first leg against span gives the service time as a function of packet length: a floor for a one-message packet and a slope per additional message, which is the cost per message that rule 4 asks for. The first leg against index within the packet gives the same slope from the other side, as a ladder. The mailbox depth against the first leg says how much of the leg was queueing.

The probe's documentation is explicit about what it cannot do, and the agent carries the same limits. There is no timestamp between the socket read and the book publish, so the first leg covers five things at once: the rest of the read loop, the wait in the first mailbox, the decode, a second mailbox hop, and the book build. A slow first leg does not say which of the five it was. The agent therefore attributes service time to a stage only by differential measurement: it flips a boundary, re-measures, and reads the stage's contribution from the difference. Nothing before the socket read is visible at all, so none of the agent's figures is a wire-to-wire latency. And every count is out of messages the book chose to publish, not messages that arrived, because the book suppresses updates that do not change the top of book before the probe sees them.

4. The agent's procedure

Inventory. The agent reads the source and the configuration and writes down the pipeline as the rules see it: the actors on the market-data path in order; at each boundary between them, whether the sender uses the synchronous call or the asynchronous send; which actors share a thread by being placed in a group; which mailbox kind each actor uses, since the spinning kinds bear on rule 7; which threads are pinned; and which stages carry state from one packet to the next, which decides under rule 6 whether a stage above the period is cut or pooled. In Kaspar-HFT the send mode is a one-line choice at the sender's call site, and the receiving handler cannot tell which was used, so this inventory is a complete description of the topology and every item in it is a dial.

Probe run. The agent builds with the probe compiled in, confirms the configuration keys the probe requires, points the output at a directory of its own so the run cannot overwrite another variant's, and runs for a window on the live feed or, in the simulator, on a recorded tape with the packets' original timestamps. It confirms from the log that the probe was created and which decode path ran. It drops the warm-up period and parses the log for recovery windows to exclude.

Measure. The publisher period from the packet gaps; the end-to-end median and p99 from the per-message records; the service floor and the slope per message from the span and index ladders; the distribution of span, and the share of decode time held by long packets.

Compare and give a verdict. Each stage's upper-quantile service against the period, which is rule 2 and the threshold of Figure 4. Each existing cut against rule 3: does removing it raise the largest stage? Each boundary's send mode against the prior of rule 5: asynchronous where the hop lowers the largest stage, synchronous everywhere else. The order of stage sizes against rule 6. Any spinning mailbox or pinned thread against rule 7: is there a measurement behind it? The run itself against rule 8.

One change, then re-measure. Where a rule is violated, or where the prior says a different setting would do better, the agent makes one change: it flips one boundary between synchronous and asynchronous, moves one actor into or out of a group, or swaps one mailbox kind. It then runs the probe again on the same tape, or on a live window matched for time of day, and compares the median and p99 with the baseline under the operator's stated trade-off between the two. An improvement is kept; anything else is reverted. The agent repeats this until no single change improves the pair, which is the stopping condition of the paper's procedure. It never makes two changes between measurements, because the joint effect of two boundaries is not the sum of their separate effects.

Report. Figure 5 shows the form. For each rule: what was measured, the threshold it was compared with, the verdict, and, where a change was made, the change and its measured effect. A separate section lists the findings the agent cannot act on, because they are not dials.

5. What the agent changes, and what it only reports

The agent changes deployment dials and nothing else: the send mode of a boundary, the grouping of actors onto threads, the mailbox kind of an actor, the pinning of a thread. In Kaspar-HFT every one of these is a configuration or a one-line change at a call site, and none of them touches a handler, a message type or a test. That is what makes the loop safe to run unattended: the system after any change passes the same tests as before, and the only question is the measured latency.

What the agent does not change is the code inside a stage. Rule 4 says that for a chain already below the period, the residual tail is in packets of many messages, decoded one after another, and in service-time variance. The agent measures both: the slope per message, and the share of packets, messages and decode time held by long packets. On NQ book the paper found that packets of ten or more messages are under 2% of packets but several times that share of messages; on ZN trade, 11% of packets hold 66% of the messages and 86% of the decode time. A finding of that kind cannot be fixed by a dial. The agent reports it with two options, both outside its remit: lower the decoder's cost per message, or move the decode onto the FPGA handler, where the work after a packet's last byte does not grow with the packet.

The agent also reports, rather than changes, anything rule 7 flags. A spinning mailbox or a pinned busy-polling thread may be right. The paper's prior is that on a self-exciting feed the receiver is already awake and warm when every tail-setting message arrives, so the intervention helps the median and the minimum and not the tail, at a steady cost in core burn and cache pressure. The agent runs the comparison with and without on the same tape and reports the three quantiles and the cost. Whether to keep it is the operator's call.

6. Using the agent

The agent runs inside Claude Code in a copy of the Kaspar-HFT repository, on a host that can reach the feed or holds a tape. A request names the handler and the window:

Check the NQ book handler against the design rules on a 15-minute live window at the open.
Audit the ES and ZN handlers on yesterday's tape, and tell me whether any boundary should change.

The agent writes the inventory, runs the probe, produces the verdicts, runs the flip loop, and leaves the report and the raw per-message records in a directory of their own. Each change it kept is a diff of one line or one configuration key, listed in the report, so the operator can see exactly what moved and revert any of it. Nothing the agent does requires an exchange credential; a live window needs only the multicast feed the host already receives.

7. Limitations

The probe measures from the socket read, so the agent cannot see the NIC, the kernel or Onload receive path, or the wire. A system that violates the rules upstream of the socket read is invisible to it. The first leg is undivided, so stage attribution rests on differential measurement, which assumes the rest of the system held still between runs; on a live feed it did not, and the agent reports live comparisons with the two windows' packet rates and span distributions beside them. Percentiles are computed on the messages the book published, not on the packets that arrived. The flip loop is a local search: it stops at a configuration no single change improves, which is what the paper's procedure specifies, and it does not claim that configuration is the global optimum. The rules themselves are those of a self-exciting feed with a bounded publisher rate; on a feed with a different arrival law the thresholds are different and the agent would need the measurement study repeated for it first. And the skill is a design: the probe, its analysis scripts, the per-boundary send modes and the mailbox kinds are in the repository and in use, and the agent that drives them against the rules is the next thing to build on top of them.

8. Conclusion

The design principles of the measurement study are rules about measured quantities, and a system either meets them on its feed or does not. Checking that is a procedure: inventory the topology, run the probe correctly, measure the period and the service times, compare, change one dial, re-measure, repeat until nothing improves, and write down what was found. Kaspar-HFT supplies the instruments and makes every topology decision a dial that can be turned without touching the code. The audit agent runs the procedure, reports which rules the system follows and which it violates, converges the dials by measurement, and names the findings that need an engineer rather than a dial.
