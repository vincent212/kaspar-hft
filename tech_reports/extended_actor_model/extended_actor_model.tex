\fs{} from CPU Threads to FPGA Pipelines}
\author{Vincent Maciejewski\\M2 Technologies\\\texttt{mayeski@gmail.com}}
\date{November 2026}

\begin{document}

\begin{abstract}
The actor model admits a single communication primitive, asynchronous send; practical
actor systems provide synchronous calls outside the model. We extend the model with a
second, synchronous primitive, \fs{}, drawn from the open-source actor framework \kh{}:
the caller blocks while the receiver handles the message, and the receiver's reply is the
return value of the call. We give \fs{} a formal semantics by extending the active-object
calculus of De Koster and De Meuter with explicit execution resources, and we prove three
properties of the extended model. \emph{Isolation}: actors share no state, and each actor
processes at most one message at a time. \emph{Determinism relative to replies}: the
outcome of a handler is a function of its message and of the replies it receives.
\emph{Conditional liveness}: under terminating handlers and fair scheduling, a handler
blocks only on a cycle of \fs{} calls, and a system without \fs{} is deadlock-free, as in
the original model. We further prove that \fs{} is not expressible as a send followed by
a blocking wait: when caller and callee share a thread, the latter deadlocks and \fs{}
does not. For debugging and deterministic replay, we show that executing all actors, in
any language and on any substrate, from a single global queue is sound with respect to
the concurrent semantics but not complete: provided that no remotely called actor shares
its thread, the global queue produces only behaviours of the concurrent system, though
not all of them. Finally, we map the extended model onto hardware. On an FPGA, \snd{} is
a FIFO between hardware processes and \fs{} is logic fused into a single process, realised
as an inline call between the actors of one group; without \fs{}, fused actors could not
call one another, since a send followed by a wait between them deadlocks. We also give
the mapping onto CPU threads and Rust, and propose one for GPUs.
\end{abstract}

% ---------------------------------------------------------------
\section{Introduction}
% ---------------------------------------------------------------

An actor encapsulates private state and communicates exclusively by message passing. In
the classic formulations \cite{hewitt1973,agha1986,agha1997} there is a single
communication primitive, asynchronous send, which places a message in the receiver's
mailbox and returns immediately. The receiver processes its messages sequentially, each
in a \emph{turn}. Since a turn never waits, turns cannot deadlock; since no state is
shared, turns cannot race. De Koster and De Meuter call this the \emph{isolated turn
principle}, give an operational semantics for four families of actor languages, and
prove the principle for each \cite{dekoster2024}.

Practical actor systems nevertheless require request/reply interaction or
synchronisation, and provide it outside the model in four forms, surveyed in
Section~\ref{sec:related-sync}: a blocking request served on the receiver's own resource
(ABCL/1, Scala Actors, Erlang/OTP, ABS, Encore, Ray); a request whose reply resumes a
suspended continuation (Akka, Orleans, CAF, Actix, E, SALSA, Pony); a direct call
permitted only within one scheduling unit (ABS cogs, E vats); and a rendezvous (CSP,
Extended Rebeca). None of them runs the receiver's ordinary handler on the caller's
resource across scheduling units and returns its result as a value.

\paragraph{\kh{} and \fs{}.} \kh{}\footnote{\kh{} is open source:
\url{https://github.com/vincent212/kaspar-hft}.} \cite{mayeski2026fastsend} is an
open-source C++20 actor framework for high-frequency and algorithmic trading. Its
trading system is venue-independent: market-data decoding, order-book reconstruction,
execution algorithms and order routing are all actors, and each exchange is connected by
its own feed handler and order session. A \kh{} actor is a
C++ object that registers one handler per message type and holds references to other
actors. The framework provides two delivery primitives. \snd{} is the classic
asynchronous send: the message is enqueued in the receiver's mailbox, the sender
proceeds, and a thread serving the receiver subsequently executes the handler. \fs{} is
synchronous: the \emph{sending} thread acquires the receiver's lock, executes the
receiver's handler inline, bypassing the mailbox, and obtains the handler's reply as the
return value of the call. The handler code is identical under both deliveries and is
independent of which one was used; the \kh{} paper calls this property \emph{receiver
transparency}. Two further extensions in \kh{} are relevant here: actor \emph{groups},
which execute a set of actors on one thread behind a single shared mailbox, and a
per-actor choice of mailbox implementation. That paper describes the framework and
measures its cost, but does not give \fs{} a formal semantics.

The subject of this paper is \fs{}, a form of synchronous communication distinct from the
three above: a synchronous send in which the caller waits while the receiver handles the
message and obtains the reply as the return value. On a CPU, the receiver's handler
executes on the caller's thread. \fs{} is neither a send followed by a blocking wait, nor
a call confined to one scheduling unit, nor a rendezvous. Synchronous communication in
actor systems is not new. Our contribution is a precise semantics for this particular
primitive, with explicit execution resources, and an exact account of its effect on
isolation, determinism, liveness, message order and single-queue simulation when those
resources are finite (Sections~\ref{sec:calculus} to~\ref{sec:debug}). We also show that
the primitive has a distinct implementation mechanism on each runtime considered, as
asynchronous send does (Section~\ref{sec:substrates}). The FPGA is the case in which
this distinction has the greatest consequence. Hardware offers two ways of connecting
computations: a FIFO between two independent processes, and logic fused into a single
process, by which FPGA designs attain their speed. \snd{} corresponds to the first, and
only \fs{} corresponds to the second: two actors fused into one process can call each
other with \fs{}, whereas a send followed by a wait between them deadlocks. With \fs{}
in the model, actors map directly onto an FPGA; without it, the second form of
connection has no counterpart in the model.

\fs{} therefore combines four properties: it executes the receiver's ordinary handler;
it reaches any actor across scheduling units in the model (\kh{} restricts it to one CPU
process, and on the FPGA to one actor group); it returns a value; and it completes on a
shared execution resource on which send-then-wait deadlocks.

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=1.6em]
  \item A thread-aware extension of the active-object calculus of
  \cite{dekoster2024} with a \fs{} rule, in two variants: the callee's turn runs on the
  caller's resource (\textsc{Fast-Local}) or on the callee's own resource while the
  caller waits (\textsc{Fast-Remote}) (Section~\ref{sec:calculus}). Both variants start
  the same method body as asynchronous delivery, which is receiver transparency stated
  in the calculus (\cref{rem:transparency}).
  \item Its properties, stated against the isolated turn principle
  (Section~\ref{sec:properties}): isolation holds (\cref{thm:isolation});
  determinism holds relative to replies (\cref{thm:determinism}); under terminating
  handlers and fair scheduling, a turn can fail to complete only if its thread can reach
  a wait-for cycle (\cref{thm:liveness}), and the
  original liveness result is the special case without \fs{}
  (\cref{cor:asynclive}); a per-thread call-chain check detects exactly the cycles
  confined to one thread (\cref{prop:localcycles}), while following the functional
  wait-for graph detects every cross-thread cycle exactly
  (\cref{lem:outdeg,prop:detect}); a \fs{} is never queued behind the
  callee's mailbox (\cref{prop:order}); \fs{} is not send-then-wait when resources are shared
  (\cref{prop:notsendwait}); and the extended calculus exhibits unbounded nondeterminism
  under its own fairness assumption through \fs{}, and under an additional delivery
  condition through \snd{} (\cref{prop:unbounded-send,prop:unbounded-fs}).
  \item Trace soundness of a single global queue as a simulator for debugging and
  deterministic replay, across languages and substrates (\cref{thm:gqsound}), its limits

  \item A mapping of both primitives onto CPU threads, a Rust runtime and an FPGA actor

  process, and fused actors can call each other only with \fs{}; a proposed mapping onto

  their implementation status in \kh{} (Section~\ref{sec:impl}).
\end{enumerate}

\section{Background: turns and the isolated turn principle}
\label{sec:background}
% ---------------------------------------------------------------

De Koster and De Meuter classify actor languages into four families (classic actors,
active objects, processes and communicating event loops) and give each a small-step
operational semantics \cite{dekoster2024}, that is, a set of rules, each of which
describes one step that a running system can take. A step is called a
\emph{reduction}, and a system \emph{reduces} by taking steps.

A \emph{configuration} is the state of the entire system at one instant: the mailbox,
data and current expression of every actor. A \emph{reduction rule} states that a
configuration of a given form may step to a configuration of another form. One rule, for
example, permits an actor that has finished its current message and has another pending
to dequeue it and begin executing the matching handler; another appends a message to the
receiver's mailbox when an actor evaluates a send. Execution is the repeated application
of rules. When several rules are applicable at once, for instance because two actors are
both ready to run, any one of them may be chosen; the possible choices correspond to the
possible interleavings of the concurrent system, so a property proved of the semantics
holds for every interleaving. We build on the active-object calculus of
\cite{dekoster2024} because it matches the programming model of the runtimes studied
here: an actor has a fixed interface, a FIFO mailbox and imperative private state.

In that calculus a configuration is the set of the system's actors. An actor is a
five-tuple $\Act{\iota_a, \mu, e, O, o}$ and a message is written $\Msg{msg,
\overline{v}}$; \cref{tab:dksymbols} gives the meaning of each symbol. In programming
terms, an actor is an object (its active object $o$) whose methods are its message
handlers, together with the data it owns (its heap $O$), the queue of messages addressed
to it (its mailbox $\mu$), and the expression it is currently evaluating ($e$).

\textsc{Send} appends a message to the receiver's mailbox after deep-copying the
passive objects it references (the function $\pass$), so that no state is shared.
\textsc{Receive} starts a turn: when an actor's expression is a value, the head of its
mailbox is removed and the matching method body becomes its expression. A \emph{turn} is
the sequence of reductions of one actor between two applications of \textsc{Receive}.

The isolated turn principle comprises two theorems \cite{dekoster2024}.
\emph{Safety}: the value to which a turn reduces is determined up to
$\alpha$-equivalence, that is, up to the choice of names for entities created during
execution, such as the identifier of a new object, irrespective of the interleaving with
other actors; moreover, a turn is not interleaved with another turn of the same actor.
\emph{Liveness}: a turn never blocks, since every reducible expression of a turn can take
a step; turns are therefore deadlock-free. Liveness holds because the calculi contain no
blocking operation.

Two features of this setting are relevant in what follows. First, the calculus has no
notion of the thread or processor that performs a reduction: each actor reduces
independently, as if it had a processor of its own. Second, every communication is a
\textsc{Send}. A synchronous call requires the former to be made explicit and introduces
a second form of communication.

\section{Synchronous communication in actor systems}
\label{sec:related-sync}
% ---------------------------------------------------------------

Three arguments are commonly advanced for excluding synchronous calls from the actor
model. \emph{Order}: in Hewitt's model messages are guaranteed to be delivered, but in
no particular order, so a request to handle a message before the sender's next action
has no meaning. \emph{Deadlock}: an actor that handles one message at a time and waits
within a turn can wait on itself, directly or transitively. \emph{Distribution}: across
machines, a synchronous call can wait indefinitely on a failed peer.

Systems that nevertheless provide request/reply differ along five axes: which execution
resource runs the callee's handler; whether the caller's thread blocks or only its
continuation is suspended; whether the caller processes other messages while the reply is
outstanding; how a cyclic call, including a call to oneself, behaves; and whether the
reply is delivered as a return value or through a future. Four families emerge
(\cref{tab:sync}).

\paragraph{Blocking request on the callee's resource.} The caller sends a request and
blocks its thread until the reply arrives, while the callee handles the request on its
own resource in a later turn. ABCL/1 distinguishes \emph{past} (asynchronous), \emph{now}
(send and wait for the reply) and \emph{future} messages \cite{yonezawa1986}. Scala Actors
provide the same form as the \texttt{!?} operator, with \texttt{!!} returning a future
instead \cite{haller2009scala}. In ABS \cite{johnsen2012abs}, a synchronous call
$v = o.m(e)$ between objects in different cogs abbreviates
$x = o!m(e);\ v = x.\mathtt{get}$: an asynchronous call followed by a blocking
\texttt{get}, which ``blocks all execution in the object until the return value is
available''. Encore's \texttt{get} likewise blocks the calling active object
\cite{brandauer2015encore}, and in Ray \texttt{ray.get} on the reference returned by an
actor method blocks the calling task \cite{moritz2018ray}. Erlang/OTP's
\texttt{gen\_server:call} sends a tagged request, monitors the callee and waits in a
selective receive for the matching reply, by default for at most 5000~ms
\cite{armstrong2003,otpgenserver}; Akka's \texttt{ask} completes a future through a
temporary actor and becomes blocking only when the caller awaits that future, which the
documentation discourages \cite{akkaask}; a blocking actor in CAF waits with
\texttt{request(\ldots).receive} \cite{charousset2016caf}. In all of these the
receiver's turn executes on the receiver's own resource, the request waits behind the
receiver's mailbox, and a cycle of requests, or a request to an actor that shares the
caller's resource, deadlocks; library forms bound the wait with a timeout rather than
detect the cycle.

\paragraph{Request with a suspended continuation.} The caller registers a continuation for
the reply and returns to its scheduler, so no thread blocks. Akka's \texttt{ask} composed
with \texttt{pipeTo}, Actix's \texttt{send}, which returns a future resolved with the
handler's result \cite{actix}, E's eventual send observed with \texttt{when}
\cite{miller2005}, SALSA's token-passing continuations \cite{varela2001salsa} and Pony's
promises \cite{clebsch2015pony} are of this kind. Whether the caller processes other
messages before the reply arrives is a design choice. CAF offers both:
\texttt{request(\ldots).then} interleaves the response handler with the actor's regular
behaviour, whereas \texttt{request(\ldots).await} suspends that behaviour until the
response arrives \cite{charousset2016caf}. The \texttt{await} of ABS and of Encore
releases the object to its other processes \cite{johnsen2012abs,brandauer2015encore}.
Orleans grain calls return tasks; grains are non-reentrant by default, so a grain that
awaits a call processes no other request, a call cycle deadlocks until the 30~s response
timeout aborts it, and reentrancy can be enabled per grain or per call chain
\cite{bykov2011orleans,orleansreentrancy}. Where interleaving is permitted, the caller's
state may change between request and reply, and the turn that issued the request is no
longer atomic; where it is not, the mechanism inherits the deadlocks of the blocking form.

\paragraph{Call within one scheduling unit.} In ABS, a synchronous call between objects
in the same cog has ``the reentrant semantics known from, e.g., Java threads''
\cite{johnsen2012abs}: control passes to the callee on the cog's single processor. In E,
immediate calls are allowed only on near references, to objects in the same vat; between
vats only eventual sends exist \cite{miller2005}. These calls execute on the caller's
processor but never cross a scheduling unit, and therefore require no mutual exclusion;
ABS, moreover, permits re-entry into an object that is already executing.

\paragraph{Rendezvous.} Sender and receiver synchronise at a matching pair of
communication actions, as in CSP \cite{hoare1978csp}. Extended Rebeca
\cite{sirjani2005jucs} groups actors (``rebecs'') into components. Components
communicate only asynchronously; inside a component, rebecs may also exchange
synchronous messages. A synchronous message has a signature but no handler: it is a
``handshake between the execution of a send-statement by the caller and a receive
statement by the callee'', and both parties block until they synchronise at that point;
data flows only from sender to receiver, and a rebec may not send a synchronous message
to itself. The receiver participates explicitly, by executing a \texttt{receive}
statement within one of its methods.

\paragraph{Expressiveness.} Honda and Tokoro \cite{hondatokoro1991} and Boudol
\cite{boudol1992} showed that synchronous communication is encodable in the asynchronous
$\pi$-calculus; \fs{} therefore does not extend the class of computable behaviours. These
encodings assume, however, that every process makes progress independently, that is,
that execution resources are unbounded. \Cref{prop:notsendwait} shows that once resources
are shared, as in an actor group or a cog, send-then-wait deadlocks where \fs{}
completes. The two primitives differ in which resource executes a turn and when.

\paragraph{Position of \fs{}.} \fs{} executes the receiver's turn on a resource on which
the caller is prepared to wait (on a CPU, the caller's own thread), across scheduling
units, under the receiver's mutual exclusion, and without re-entry: an actor that is
already in a turn cannot be entered again, and a call that attempts to enter it waits,
possibly indefinitely. It thus combines the local execution of calls within a scheduling
unit with the unrestricted reach of send-then-wait, at the cost of a deadlock case that
calls within a scheduling unit do not have. In contrast to a rendezvous, the receiver
does not participate: its ordinary handler runs as a complete turn, and its result is
returned as a value. Unlike the continuation-based forms, it neither suspends nor
interleaves the caller's turn, which therefore remains atomic. \Cref{tab:sync}
summarises the differences, which the remainder of the paper makes precise.

% ---------------------------------------------------------------
\section{A thread-aware calculus with \fs{}}
\label{sec:calculus}
% ---------------------------------------------------------------

Reasoning about \fs{} requires a precise, step-by-step account of its behaviour in the
same terms as the rest of the actor model. We obtain one by extending the calculus of
Section~\ref{sec:background} rather than defining a new one, so that every property the
original calculus establishes for \snd{} continues to hold and the new rules are the only
point at which \fs{} can affect behaviour.

The original calculus does not specify \emph{which} agent executes an actor's code: each
actor takes steps as if it had a processor of its own. This suffices for asynchronous
send, which never waits, but not for \fs{}. Whether a synchronous call completes depends
on which thread executes the callee's handler and on the other activity of that thread:
on an idle thread the call completes, whereas on a thread that is itself waiting it may
never start. The first extension therefore makes execution resources (threads) part of
the model and records, for each thread, the stack of handlers whose execution it has
begun and not finished, as a call stack does in a sequential program. The second adds
\fs{} itself, in two forms: the callee's handler executes either on the caller's thread
or on a thread of its own while the caller waits.

Concretely, we extend the active-object calculus of \cite{dekoster2024} in three
respects: execution resources become explicit, an actor's current expression moves from
the actor into a \emph{frame} on a resource's stack, and a \fs{} expression is added. We
refer to the resources as \emph{threads}; on an FPGA they are hardware processes
(Section~\ref{sec:substrates}).

\subsection{Semantic entities and syntax}

\begin{align*}
K &\in \text{Configuration} ::= \langle A, T\rangle\\
a &\in A \subseteq \text{Actor} ::= \Act{\iota_a, \mu, O, o, \theta}\\
t &\in T \subseteq \text{Thread} ::= \Thr{\theta, S}\qquad S ::= \epsilon \mid S\cdot f\\
f &\in \text{Frame} ::= \Frm{\iota_a, e, \kappa}\qquad \kappa ::= \turn \mid \ret{\rho}
\end{align*}

An actor has an identifier, a FIFO mailbox $\mu$, a heap $O$, an active object $o$, and
a \emph{home thread} $\theta$. Several actors may share a home thread; that is an actor
group. A thread has an identifier and a stack $S$ of frames, top on the right. A frame
records which actor it belongs to, the expression being evaluated, and why it exists:
$\turn$ for a turn started from the mailbox, or $\ret{\rho}$ for a turn started by the
\fs{} call $\rho$, whose value must be returned. Call identifiers $\rho$ are fresh.
\Cref{tab:oursymbols} summarises the new symbols. In programming terms, a thread is a
call stack, each frame on it is one actor's handler in progress, and a \fs{} that
executes on the caller's thread pushes the callee's handler above the caller's, as a
function call does.

$\kappa = \ret{\rho}$ & the frame is a turn started by \fs{} call $\rho$; its result goes back to the caller \\ \rowsep
$\rho$ & a \fs{} call's identifier, new for each call \\ \rowsep
$\fsend(\iota_b, msg, \overline{v})$ & the \fs{} expression: call actor $\iota_b$'s handler $msg$ with arguments $\overline{v}$ \\ \rowsep
$\wait{\rho}$ & where a caller's expression waits for the result of call $\rho$ \\ \rowsep
$\busy_K(\iota_a)$ & actor $\iota_a$ has a handler in progress somewhere in $K$ \\ \rowsep
$\body(a, msg, \overline{v})$ & the code of actor $a$'s handler for $msg$, with its arguments filled in \\ \rowsep
$v$ & a value: an expression that has finished computing \\ \rowsep
$m \cdot \mu$,\ $S \cdot f$ & the mailbox $\mu$ with message $m$ at its head; the stack $S$ with frame $f$ pushed on top \\ \rowsep
$K \red K'$ & configuration $K$ can take one step, to $K'$ \\ \rowsep
$K \red^* K'$ & $K$ can reach $K'$ in zero or more steps \\
\bottomrule
\end{tabular}
\end{table}

The expression syntax of the active-object calculus is extended with one form, and the
run-time syntax with one more:
\[
e ::= \dots \mid \fsend(e, msg, \overline{e})\qquad\qquad
e ::= \dots \mid \wait{\rho}\ \ \text{(run time)}
\]
A production $e ::= \dots \mid X$ extends the existing grammar of expressions with the
form $X$: a program may now contain $\fsend(e, msg, \overline{e})$, and while a call is
in progress the runtime replaces the call by $\wait{\rho}$. The form $\wait{\rho}$ does
not occur in source programs.

An \emph{evaluation context} $\mathcal{E}$ is an expression with a single hole, which
marks the subexpression to be evaluated next; $\ctx{e'}$ denotes the expression with
$e'$ in the hole. In $x + \fsend(\iota_b, msg, 1)$, for instance, the context is
$x + [\ ]$ and the \fs{} is evaluated next. Evaluation contexts fix the order of
evaluation; we extend those of the original calculus left to right through the arguments
of $\fsend$, so the arguments are evaluated before the call is made. No rule reduces
$\wait{\rho}$: a frame whose expression has the form $\ctx{\wait{\rho}}$ is suspended at
the call and is said to be \emph{waiting}.

\begin{definition}[Busy]
Actor $\iota_a$ is \emph{busy} in $K$, written $\busy_K(\iota_a)$, if some thread of $K$
has a frame of $\iota_a$ on its stack.
\end{definition}

An actor's active object is written $o = \Obj{\iota_o, cls, \overline{v_f}}$: its
identifier $\iota_o$, its class $cls$, and the values of its fields $\overline{v_f}$. For
such an actor and a message $\Msg{msg, \overline{v}}$, let $\body(a, msg, \overline{v})$
be the body of method $msg$ of $cls$ with the fields, the parameters and $\mathsf{self}$
replaced by their values, as in \textsc{Receive} and \textsc{Invoke} of
\cite{dekoster2024}; it is the code that the handler executes.

\subsection{Reduction rules}

The actor-local rules of \cite{dekoster2024} apply unchanged to the \emph{top} frame of
any thread, reading and writing the heap of the frame's actor. \textsc{Send} and
\textsc{Self-Send} likewise apply to a top frame and append to the receiver's mailbox.
\textsc{Spawn} creates an actor with an empty mailbox and a home thread, either an
existing one or a fresh $\Thr{\theta', \epsilon}$. \textsc{Receive} and the end of a turn
become thread rules, and three rules are new (\cref{fig:rules}).

Each rule in \cref{fig:rules} states that if the premises above the line hold, the
system may take the step below the line. The premises are side conditions, for example
that a thread's stack is empty; the conclusion is a step $K \red K'$, where $K'$ is $K$
with some threads or actors replaced, as denoted by $K[t \mapsto t']$.

\Cref{fig:rulestacks} shows the effect of each rule on the thread stacks involved. Read
in terms of premises and effect, the rules are as follows.

\begin{itemize}[leftmargin=1.4em]
  \item \textsc{Receive}. \emph{Premises}: thread $\theta$ is idle (its stack is
  $\epsilon$); actor $a$ has home thread $\theta$, the message $\Msg{msg,\overline{v}}$
  at the head of its mailbox, and no frame on any thread. \emph{Effect}: the message is
  removed from the mailbox and a frame for $a$, evaluating the handler
  $\body(a,msg,\overline{v})$ and tagged $\turn$, becomes the only frame on $\theta$. When
  several actors share $\theta$, the choice among those with non-empty mailboxes is
  unconstrained.
  \item \textsc{Turn-End}. \emph{Premise}: the top frame of a thread is a $\turn$ frame
  whose expression has reduced to a value $v$. \emph{Effect}: the frame is popped and $v$
  is discarded; a reply to a \snd{} is itself an explicit \snd{}.
  \item \textsc{Fast-Local}. \emph{Premise} $\mathsf{Call}(t,\iota_b,\rho)$: the top frame
  on thread $\theta$ belongs to actor $\iota_a$ and is about to evaluate
  $\fsend(\iota_b,msg,\overline{v})$, the callee $\iota_b$ has no frame on any thread, and
  $\rho$ is a fresh call identifier. \emph{Effect}: the caller's \fs{} expression is
  replaced by $\wait{\rho}$ (frame $W_\rho$), and the callee's handler is pushed on the
  \emph{same} thread above it as frame $C_\rho$, tagged $\ret{\rho}$. The callee's home
  thread and mailbox are not involved. The rule models \fs{} on one CPU thread, or
  between the actors of one FPGA group.
  \item \textsc{Fast-Remote}. \emph{Premises}: $\mathsf{Call}(t,\iota_b,\rho)$, and in
  addition the callee's home thread $\theta_b$ differs from $\theta$ and is idle.
  \emph{Effect}: the caller's frame becomes $W_\rho$ on $\theta$, and $C_\rho$ becomes the
  only frame on $\theta_b$. The caller's thread holds the waiting frame and can make no
  further progress until the call returns. The rule models \fs{} to an actor on another
  resource on which the caller waits, such as a dedicated FPGA process or another
  machine. The rule is part of the model,
  and the results below hold for it.
  \item \textsc{Fast-Return}. \emph{Premises}: the top frame of some thread $\theta'$ is
  the callee frame of call $\rho$ and has reduced to a value $v$; some thread $\theta$
  holds the caller's frame waiting on $\rho$. \emph{Effect}: the callee frame is popped,
  and the copy $v' = \pass(v)$ replaces $\wait{\rho}$ in the caller's expression, which
  resumes. After \textsc{Fast-Local}, $\theta' = \theta$ and the two frames are
  adjacent; after \textsc{Fast-Remote}, they are on different threads.
\end{itemize}

\paragraph{A worked reduction.} Let actors $a$ and $b$ have home threads $\theta_1$ and
$\theta_2$, let $b$'s handler for $\mathit{get}$ return its field $x$, and let $a$'s
handler for $\mathit{go}$ evaluate $\fsend(\iota_b, \mathit{get}, \epsilon) + 1$. Starting
from idle threads and $\Msg{\mathit{go}}$ in $a$'s mailbox, the system reduces as
follows.
\begin{enumerate}[leftmargin=1.6em]
  \item \textsc{Receive} on $\theta_1$: $\theta_1 = \Thr{\theta_1,
  \Frm{\iota_a, \fsend(\iota_b,\mathit{get},\epsilon)+1, \turn}}$, and $a$'s mailbox is
  empty.
  \item \textsc{Fast-Local}, since $b$ is idle: $\theta_1 = \Thr{\theta_1,
  \Frm{\iota_a, \wait{\rho}+1, \turn}\cdot\Frm{\iota_b, \body(b,\mathit{get},\epsilon),
  \ret{\rho}}}$. Thread $\theta_2$, $b$'s home thread, is not involved and may meanwhile
  run turns of other actors; a message already in $b$'s mailbox is not consulted.
  \item Actor-local steps reduce $b$'s frame to the value of $x$, say $4$.
  \item \textsc{Fast-Return}: $b$'s frame is popped and $\theta_1 = \Thr{\theta_1,
  \Frm{\iota_a, 4+1, \turn}}$.
  \item Actor-local steps reduce $a$'s frame to $5$, and \textsc{Turn-End} leaves
  $\theta_1$ idle.
\end{enumerate}
Had $b$ been in a turn at step~2, the premise $\neg\busy_K(\iota_b)$ would fail and $a$'s
frame would be blocked until $b$'s turn ended; under \textsc{Fast-Remote}, step~2 would
instead place $b$'s frame on $\theta_2$, provided $\theta_2$ were idle.

Two distinct conditions govern a \fs{}, and the distinction is used throughout.
\emph{Actor availability}: both rules require the callee actor to be idle, that is, to
have no frame on any thread. \emph{Resource availability}: \textsc{Fast-Remote}
additionally requires the callee's home thread to be idle. An actor can be idle while its
home thread is busy running another actor's turn; \textsc{Fast-Local} then still applies,
because it does not use the callee's thread, but \textsc{Fast-Remote} does not. When the
condition of the chosen rule fails, the calling frame is \emph{blocked}. The callee's
mailbox is never consulted. A system may use \textsc{Fast-Local} for some pairs of actors
and \textsc{Fast-Remote} for others; every result below holds for any such mixture.
\Cref{fig:sendfast} shows \snd{} and \textsc{Fast-Local} side by side.

\begin{remark}[What \fs{} does not provide]
\label[remark]{rem:notprovided}
\fs{} is not a function call. It does not enter an actor that is already in a turn:
re-entry is excluded, and a call to a busy actor waits. It does not guarantee that the
call completes (\cref{thm:liveness}), and hence does not guarantee deadlock freedom. It
is not a priority mechanism: although it is not queued behind the callee's mailbox
(\cref{prop:order}), it does not interrupt a turn in progress. It provides no timing
guarantee, no failure handling (a call to an actor whose resource has failed waits
indefinitely), and no transactional semantics across the actors called within a turn.
\end{remark}

\begin{remark}[Receiver transparency]
\label[remark]{rem:transparency}
A method body cannot tell how its turn started: \textsc{Receive}, \textsc{Fast-Local} and
\textsc{Fast-Remote} all install the same $\body(b, msg, \overline{v})$. This is the
calculus counterpart of receiver transparency in \kh{} \cite{mayeski2026fastsend}. It is
a property of the interface presented to a turn, not a claim about what code in a real
language can observe of its execution context.
\end{remark}

% ---------------------------------------------------------------
\section{Properties}
\label{sec:properties}
% ---------------------------------------------------------------

We now determine the effect of \fs{} on the guarantees of the actor model. The isolated
turn principle of De Koster and De Meuter (Section~\ref{sec:background}) has two halves,
which we consider in turn.

\begin{itemize}[leftmargin=1.4em]
  \item \emph{Isolation} (Section~\ref{sec:iso}). Each actor still handles one message at
  a time, and no other code accesses its state: \fs{} never starts a second handler of
  the same actor and never gives one actor access to another's data.
  \item \emph{Determinism} (Section~\ref{sec:det}). A handler's outcome remains
  determined by its input, provided that the replies it receives are counted as input.
  \item \emph{Liveness} (Section~\ref{sec:live}). A handler need not complete: a caller
  can wait indefinitely. We characterise exactly when this occurs, namely only when waits
  form a cycle, and show that without \fs{} the original guarantee is recovered.
\end{itemize}

Two further results distinguish \fs{} from constructs with which it might be confused.
Section~\ref{sec:order} states its interaction with message order, and
Section~\ref{sec:notsw} shows that it is not a send followed by a blocking wait: the two
differ when actors share a thread.

The statements quantify over every configuration reachable by the rules. Throughout, $K_0
\red^* K$ ranges over configurations reachable from an initial configuration with one
actor, as in \cite{dekoster2024}, whose single thread holds no frames.

\subsection{Isolation}
\label{sec:iso}

Isolation permits reasoning about one actor at a time: while a handler executes, no
other code modifies the actor's state, and the handler cannot access the state of any
other actor. A synchronous call might appear to compromise this property, since the
caller's handler is suspended partway through while another handler runs. We show that
it does not. The argument rests on a single invariant, that every actor has at most one
handler in progress in the entire system, from which isolation follows directly.


\begin{lemma}[One frame per actor]
\label[lemma]{lem:oneframe}
In every reachable configuration, each actor has at most one frame, and every frame reads
and writes only the heap of its own actor.
\end{lemma}
\begin{proof}
Initially there are no frames. Only \textsc{Receive}, \textsc{Fast-Local} and
\textsc{Fast-Remote} create frames, and each creates a frame for an actor that is not
busy, that is, has no frame. \textsc{Turn-End} and \textsc{Fast-Return} only remove
frames; the other rules rewrite the expression of an existing top frame. The heap
discipline is that of the active-object calculus: field access and update apply to the
heap of the frame's actor, and values crossing actors (\textsc{Send}, the two \fs{} rules,
\textsc{Fast-Return}) are copied by $\pass$.
\end{proof}

\begin{definition}[Turn]
A turn of $\iota_a$ is the sequence of reductions from the creation of a frame of
$\iota_a$ (by \textsc{Receive}, \textsc{Fast-Local} or \textsc{Fast-Remote}) to its
removal (by \textsc{Turn-End} or \textsc{Fast-Return}).
\end{definition}

\begin{theorem}[Isolation]
\label{thm:isolation}
No two turns of the same actor overlap, and during a turn of $\iota_a$ the heap of
$\iota_a$ is changed only by reductions of that turn's frame.
\end{theorem}
\begin{proof}
Immediate from \cref{lem:oneframe}: a second turn would need a second frame.
\end{proof}

\Cref{thm:isolation} is the safety half of the isolated turn principle, which therefore
holds in the presence of \fs{}. A turn that performs a \fs{} is suspended while the
callee runs, but no other turn of the same actor can run in the interval, and the callee
cannot access the caller's state.

\subsection{Determinism relative to replies}
\label{sec:det}

Determinism states that a handler's result is fixed by its input, irrespective of the
concurrent activity of other actors; it is the property that allows a handler to be
tested in isolation. With \fs{}, a handler receives additional input during its
execution: the reply to each call it makes, whose value depends on the callee's state at
the time of the call. We show that the replies are the only new source of
nondeterminism: a handler is as deterministic as before, once its replies are counted
among its inputs.


In \cite{dekoster2024} the value of a turn is determined, because a turn receives no
input after it starts. With \fs{} this no longer holds: each \textsc{Fast-Return}
substitutes a value that depends on the callee's state, which other turns may have
modified before the call.

\begin{theorem}[Determinism relative to replies]
\label{thm:determinism}
Consider two turns of the same actor that start from $\alpha$-equivalent heaps and
expressions. If the values substituted into them by \textsc{Fast-Return}, in order, are
$\alpha$-equivalent, then the two turns end with $\alpha$-equivalent values and heaps and
issue $\alpha$-equivalent \snd{} and \fs{} requests in the same order.
\end{theorem}
\begin{proof}
As the safety proof of \cite{dekoster2024}, by induction on the reductions of the turn's
frame: evaluation contexts fix the order of reduction, and every actor-local rule
produces $\alpha$-equivalent results from $\alpha$-equivalent inputs. The new cases are
the two \fs{} rules, which rewrite the frame to $\ctx{\wait{\rho}}$ and perform no
reduction on it until \textsc{Fast-Return}, whose substituted value is
$\alpha$-equivalent by hypothesis. Reductions of other frames do not touch this turn's
heap (\cref{lem:oneframe}).
\end{proof}

A turn that performs no \fs{} satisfies the original safety theorem unchanged. A turn
that performs one is deterministic as a function of its replies, as it would be if the
replies were messages; what \fs{} excludes is the handling of any other message of the
same actor between the request and the reply.

\subsection{Liveness}
\label{sec:live}

Liveness states that every handler that starts eventually completes. In the original
model it holds because no operation waits. A \fs{} waits, so liveness can fail; we
characterise exactly when. We first define the wait-for relation between threads as a
graph, and then show that a handler can fail to complete if and only if its
thread has a path in that graph to a cycle of threads, each waiting for the next.
Without \fs{} the graph has no edges, so the original guarantee is a special case.
Finally, we determine what a check confined to a single thread can and cannot detect.


\begin{definition}[Blocked frame, wait-for graph]
A top frame $\Frm{\iota_a, \ctx{\fsend(\iota_b, msg, \overline{v})}, \kappa}$ on thread
$\theta$ is \emph{blocked} in $K$ if the \fs{} rule used for that call does not apply to it. The \emph{wait-for
graph} $\mathit{WF}_K$ has the threads of $K$ as nodes and an edge $\theta \to \theta'$ when either
\begin{enumerate}[label=(\roman*),leftmargin=2em]
  \item the top frame of $\theta$ is blocked on $\iota_b$ and $\theta'$ holds the frame
  of $\iota_b$; or it is blocked by \textsc{Fast-Remote} because $\iota_b$'s home thread
  $\theta'$ is not idle; or
  \item $\theta$ holds a waiting frame $\ctx{\wait{\rho}}$ whose callee frame $\ret{\rho}$
  is on $\theta' \neq \theta$.
\end{enumerate}
\end{definition}

\Cref{fig:waitfor} shows both kinds of edge. Every edge leaves a thread that cannot

callee's.

The liveness result is not a termination theorem for arbitrary actor programs. We
assume that every handler terminates once the \fs{} calls it makes have returned, and
that scheduling is fair. Fairness has two components. The first is standard: a thread
whose top frame is reducible is eventually reduced. The second concerns blocked calls:
when a busy callee's turn ends, the calculus permits its home thread to start its next
mailbox turn before the waiting \fs{} is applied, and this can recur indefinitely,
starving the caller. We therefore also assume that a \fs{} that becomes applicable
infinitely often is eventually applied. A runtime whose lock provides no fairness
guarantee does not satisfy this assumption; the preference for pending calls in
\cref{prop:order} does. The CPU runtime of \kh{} acquires a plain mutex, which provides
no such guarantee. Under these assumptions the only remaining source of non-termination
is cyclic waiting, which \fs{} introduces; a handler that diverges violates the
assumption and lies outside the scope of the result.

\begin{assumption}[Terminating handlers, fair scheduling]
\label[assumption]{ass:fair}
(a) Every method body terminates when its \fs{} calls return. (b) Every thread whose top
frame can be reduced is eventually reduced. (c) A blocked \fs{} whose rule becomes
applicable infinitely often is eventually applied.
\end{assumption}

\begin{theorem}[Liveness and wait-for cycles]
\label{thm:liveness}
Under \cref{ass:fair}, a turn in a reachable configuration $K$ fails to complete in some
fair continuation of $K$ if and only if, in some configuration reachable from $K$, its
thread has a path in the wait-for graph to a cycle.
\end{theorem}
\begin{proof}
($\Leftarrow$) Take the cycle $\theta_1 \to \dots \to \theta_n \to \theta_1$. Each
$\theta_i$ waits for a frame on $\theta_{i+1}$ to be removed. That frame is below the top
of $\theta_{i+1}$ or is its top; in either case its removal needs $\theta_{i+1}$ to
progress, which needs a frame on $\theta_{i+2}$ removed, and so on around the cycle. No
rule removes a frame of a thread whose top frame is blocked or waiting, so none of the
$\theta_i$ ever progresses, and a thread with a path to the cycle waits on it
indefinitely.

($\Rightarrow$) Under \cref{ass:fair}, a frame that can be reduced is eventually reduced
and, its body terminating, eventually removed. Hence a turn that never completes must,
from some point on, reside on a thread that is permanently blocked or waiting; we show that
this requires a path to a cycle. Suppose not: in every configuration reachable from $K$,
the path from $\theta$ in $\mathit{WF}_K$ is finite and acyclic. Its last thread $\theta^*$ has no
outgoing edge, so its top frame is neither blocked nor waiting on another thread, and it
is reduced until it is removed by \textsc{Turn-End} or \textsc{Fast-Return}. Each such
removal either brings $\theta^*$ closer to removing the frame its predecessor on the path
waits for (there are finitely many frames above it) or removes that frame, after
which the predecessor's waiting frame resumes or its blocked \fs{} becomes applicable,
and by part (c) of \cref{ass:fair} is eventually applied. Induction on
the length of the path then shows that $\theta$ itself progresses, contradicting the
assumption that its turn never completes.
\end{proof}

\begin{corollary}[Liveness without \fs{}]
\label[corollary]{cor:asynclive}
If a program never evaluates $\fsend$, every turn completes under \cref{ass:fair}.
\end{corollary}
\begin{proof}
Without \fs{} there are no blocked or waiting frames, so the wait-for graph has no edges.
\end{proof}

\Cref{cor:asynclive} recovers the liveness half of the isolated turn principle as the
case without \fs{}. With \fs{}, liveness is a property of the program's pattern of
synchronous calls rather than of the model.

\begin{proposition}[What a per-thread call chain detects]
\label[proposition]{prop:localcycles}
Suppose a thread checks, before each \fs{} to $\iota_b$, whether $\iota_b$
has a frame on its own stack. The check succeeds exactly for the self-loops
$\theta \to \theta$ of the wait-for graph. It does not detect cycles of length two or
more.
\end{proposition}
\begin{proof}
A self-loop arises when the top frame of $\theta$ is blocked on an actor whose frame is on
$\theta$ itself, which is what the check tests. A cycle through two threads
$\theta_1 \to \theta_2 \to \theta_1$ arises when the top frame of each is blocked on an
actor whose frame is on the other: each check inspects only its own stack, finds the
callee absent, and passes. For example, thread~1 runs a \fs{} to $A$ whose body makes a
\fs{} to $B$, while thread~2 runs a \fs{} to $B$ whose body makes a \fs{} to $A$.
\end{proof}

\subsection{Deadlock detection}
\label{sec:detect}

Detection is simpler than in general lock-based systems because the wait-for graph of the
calculus is functional: no thread waits for more than one other.

\begin{lemma}[At most one wait-for edge per thread]
\label[lemma]{lem:outdeg}
In every reachable configuration, every frame of a thread other than its top frame is a
waiting frame whose callee frame lies immediately above it, and every thread has at most
one outgoing edge in the wait-for graph.
\end{lemma}
\begin{proof}
By induction on reductions. \textsc{Receive} applies only to an idle thread and creates a
single frame. \textsc{Fast-Local} turns the top frame into a waiting frame and pushes its
callee directly above it. \textsc{Fast-Remote} leaves the waiting frame on top of the
caller's thread and creates the callee frame as the only frame of an idle thread.
\textsc{Fast-Return} and \textsc{Turn-End} remove a top frame, and actor-local rules
change only a top frame. Hence only the top frame of a thread can be blocked, or waiting
on a callee held by another thread. An edge of kind (i) leaves a blocked top frame and
points to the unique thread that holds the callee's frame (\cref{lem:oneframe}) or, under
\textsc{Fast-Remote}, to the callee's home thread; an edge of kind (ii) leaves a top
frame waiting on a callee held elsewhere. The two cases exclude each other, so each
thread has at most one outgoing edge.
\end{proof}

By \cref{lem:outdeg} the wait-for graph is a partial function on threads, and by the
($\Leftarrow$) direction of \cref{thm:liveness} a cycle, once formed, is permanent: no
thread on it takes another step. A thread is therefore deadlocked exactly when following
the successor function from it revisits a thread, and a deadlock can be found by
following a chain of pointers rather than by searching a graph.

\begin{proposition}[Exact detection by chain following]
\label[proposition]{prop:detect}
Suppose that (1) each actor records the thread that holds its frame, if any; (2) a
thread publishes its outgoing wait-for edge before it blocks or waits, and withdraws it
before it resumes; (3) these records carry a version number incremented on every write, and are
written and read with sequentially consistent operations; and (4) a thread that
publishes an edge then follows the chain of published edges from itself twice, and
accepts the chain only if every record on it has the same version in both traversals. Then a chain accepted as
returning to its start is a cycle of the wait-for graph of a reachable configuration,
hence a deadlock, and every cycle of the wait-for graph is accepted by at least one of
the threads on it.
\end{proposition}
\begin{proof}
\emph{Soundness.} If every record on the chain has the same version in both traversals,
no record was written between its two reads, so all the edges read held simultaneously
at the instant between the end of the first traversal and the start of the second; they
therefore form a cycle of the wait-for graph of the configuration at that instant, which
by \cref{thm:liveness} is a deadlock. \emph{Completeness.} Let a cycle be formed, and
let $\theta$ be the thread on it whose edge was published last. By (3), when $\theta$
follows the chain, every other edge of the cycle is visible to it, and by permanence of
the cycle none of them changes during either read; the chain from $\theta$ therefore
returns to $\theta$ and is accepted. If several threads close cycles concurrently, the
sequentially consistent order of their publications identifies a last one for each
cycle, and the argument applies to it.
\end{proof}

\paragraph{Implementation.} In the CPU runtime of \kh{}, the record of (1) is the owner of
the callee's \fs{} lock, and an edge of kind (i) is published when an attempt to acquire
that lock fails, before the thread waits for it. The uncontended \fs{} therefore costs
nothing extra: the chain is followed only on the path that blocks, and its length is at
most the number of threads. A detected cycle requires a resolution policy: the call
that closes the cycle can fail with an error, as the per-thread check does for
self-loops; it can fall back to asynchronous delivery, at the cost of the atomicity of
the calling turn; or a victim turn can be aborted, as in database deadlock detection.
Prevention is the alternative to detection: \cref{prop:callgraph} shows that an acyclic
call graph excludes deadlock statically, and a global order on actors that every \fs{}
respects produces such a graph. On the FPGA, \fs{} is confined to one group and compiled
to an inline call, and Vitis HLS does not synthesise recursive functions, so a design
whose group-internal calls form a cycle is rejected when it is built.

\subsection{Unbounded nondeterminism}
\label{sec:unbounded}

A system has \emph{unbounded nondeterminism} if it is guaranteed to terminate and yet can
terminate in any of infinitely many states. Dijkstra's guarded commands exclude it: a
program that always terminates has only finitely many outcomes from a given state
\cite{dijkstra1976}. Clinger showed that the actor model admits it, because message
delivery is guaranteed while its delay is unbounded \cite{clinger1981}. The standard
witness is a counter: an actor increments a counter and sends itself \texttt{go} until it
receives \texttt{stop}; delivery of \texttt{stop} is guaranteed, so the counting
terminates, but it may terminate with any value. We examine how this property relates to
\cref{ass:fair}, to \fs{}, and, in Section~\ref{sec:gq-incomplete}, to the global-queue
simulator.

\paragraph{Bounded and unbounded nondeterminism.} A program has \emph{bounded}
nondeterminism if, from every state, each step has finitely many possible successors and
every execution terminates; by K\"onig's lemma its tree of executions is then finite, so
from a given state it has finitely many outcomes, and all of them can be enumerated by a
finite search. Dijkstra adopted this restriction deliberately: the weakest-precondition
semantics of guarded commands is continuous only when nondeterminism is bounded, and he
regarded unbounded nondeterminism as unimplementable \cite{dijkstra1976}. Semantics that
admit unbounded (countable) nondeterminism lose this continuity and require
fixed points beyond the first infinite ordinal \cite{aptplotkin1986}.

The actor counter has finite branching at every step, so it does not escape K\"onig's
lemma by branching; it escapes it through fairness. Its tree of executions contains an
infinite path, the one on which $b$'s thread never takes a step and $c$ counts
indefinitely, and fairness excludes exactly that path. Every remaining execution is
finite, yet there are infinitely many of them, and so infinitely many outcomes. Fairness
is a constraint on infinite executions as a whole, not on individual steps, which is why
no step-wise bound can express it. Clinger and Hewitt regard this as an essential feature
of the actor model rather than a defect: a server that is guaranteed to answer every
request, after an arbitrary but finite delay, has unbounded nondeterminism, and a model
restricted to bounded nondeterminism cannot express that guarantee
\cite{clinger1981}.

Two consequences matter here. First, any liveness result that relies on fairness, such as
\cref{thm:liveness}, holds in a setting with unbounded nondeterminism, and its proof
cannot proceed by finite enumeration of outcomes. Second, the outcomes of a program with
unbounded nondeterminism cannot be covered by any finite set of test runs, in simulation
or otherwise; \cref{prop:gqdet} makes this concrete for the global queue, which produces
exactly one of them.

\paragraph{Fairness and delivery.} \Cref{ass:fair} constrains the reduction of frames that
already exist and the application of blocked \fs{} calls; it contains no guarantee that a
message in a mailbox is ever received. The original liveness half of the isolated turn
principle concerns the completion of turns, not the delivery of messages, and
\cref{thm:liveness} inherits that scope. Clinger's setting corresponds to the following
additional condition.

\begin{assumption}[Fair delivery]
\label[assumption]{ass:delivery}
If, in infinitely many configurations of an execution, actor $\iota_a$ has a non-empty
mailbox and its home thread is idle, then \textsc{Receive} is eventually applied to
$\iota_a$.
\end{assumption}

Consider the counter of the introduction to this subsection. Actor $c$, with fields $x =
0$ and $s = \mathit{false}$, has a handler for \texttt{go} that does nothing if $s$ holds
and otherwise increments $x$ and sends \texttt{go} to $c$, and a handler for
\texttt{stop} that sets $s$. Actor $b$ has a handler for \texttt{start} that sends
\texttt{stop} to $c$. The actors have distinct home threads; initially $c$'s mailbox
holds \texttt{go} and $b$'s holds \texttt{start}.

\begin{proposition}[Unbounded nondeterminism with \snd{}]
\label[proposition]{prop:unbounded-send}
Under \cref{ass:fair,ass:delivery}, every fair execution of the counter reaches a
configuration in which all threads are idle and all mailboxes empty, and for every $n
\geq 1$ some fair execution reaches such a configuration with $x = n$. Under
\cref{ass:fair} alone, termination is not guaranteed.
\end{proposition}
\begin{proof}
For $n \geq 1$, let $c$'s home thread run $n-1$ complete turns for \texttt{go} before
$b$'s home thread takes any step; this finite prefix is extended to a fair execution.
After it, $x = n-1$ and $c$'s mailbox holds one \texttt{go}. The turn of $b$ then appends
\texttt{stop} behind that \texttt{go}, which, received next, sets $x = n$; \texttt{stop}
then sets $s$, and every later \texttt{go} turn sends nothing. Termination of every fair
execution: by \cref{ass:delivery} the turn of $b$ starts, and by \cref{cor:asynclive} it
completes, appending \texttt{stop}. Each \texttt{go} turn appends at most one message, so
finitely many messages precede \texttt{stop} in $c$'s FIFO mailbox, and by
\cref{ass:delivery} all of them and \texttt{stop} are received; afterwards at most one
\texttt{go} remains, which sends nothing. Without \cref{ass:delivery}, the execution in
which no \textsc{Receive} is ever applied satisfies \cref{ass:fair} and does not
terminate.
\end{proof}

\paragraph{The effect of \fs{}.} The counter uses only \snd{}, and the extended calculus
contains the original, so unbounded nondeterminism under \cref{ass:delivery} is
unaffected by the addition of \fs{}. Part~(c) of \cref{ass:fair} has a further
consequence: it is a fairness guarantee for synchronous delivery, and it yields unbounded
nondeterminism without \cref{ass:delivery}. Let $b$'s turn instead evaluate
$\fsend(\iota_c, \mathtt{stop}, \epsilon)$, with \texttt{stop} as above, and let the
initial configuration contain that turn on $b$'s home thread.

\begin{proposition}[Unbounded nondeterminism with \fs{}]
\label[proposition]{prop:unbounded-fs}
Under \cref{ass:fair} alone, with \fs{} applied by \textsc{Fast-Local}, every fair
execution of this variant reaches a configuration in which $s$ holds and $x$ no longer
changes, and for every $n \geq 0$ some fair execution reaches such a configuration with
$x = n$.
\end{proposition}
\begin{proof}
\textsc{Fast-Local} for the call requires only that $c$ have no frame on any thread. If
$c$'s home thread applies \textsc{Receive} infinitely often, $c$ is idle between any two
of its turns; otherwise it is idle from some point on. In either case the rule is
applicable infinitely often, so by part~(c) of \cref{ass:fair} it is applied, and by
parts~(a) and~(b) the turn for \texttt{stop} completes on $b$'s thread, setting $s$
while no turn of $c$ is in progress. Every later \texttt{go} turn sends nothing, so $x$
no longer changes. For $n \geq 0$, apply the call after exactly $n$ complete \texttt{go}
turns of $c$; each delay is finite, so the execution is fair, and $x = n$ when $s$ is set.
\end{proof}

\Cref{prop:unbounded-fs} shows that \fs{} introduces no new form of nondeterminism but
makes the existing one observable within a single turn. By \cref{thm:determinism}, a turn
is a function of the replies it receives, and a reply may range over an unbounded set:
a turn that evaluates $\fsend(\iota_c, \mathtt{get}, \epsilon)$ on the counter receives
some $x \in \mathbb{N}$ that the program does not determine. Determinism relative to
replies therefore locates the nondeterminism precisely, in the replies, without bounding
it. The global-queue simulator of Section~\ref{sec:debug}, by contrast, is deterministic
and exhibits exactly one of these outcomes (\cref{prop:gqdet}).

\subsection{Order}
\label{sec:order}

Programs depend on the order in which messages arrive. We state the ordering guarantees
that hold when \snd{} and \fs{} are combined: messages sent by one actor to another
still arrive in the order sent; a \fs{} is not queued behind messages already pending
for the callee; and every message the callee sends while handling a \fs{} is enqueued
before any message the caller sends after the call returns.


\begin{proposition}[Order]
\label[proposition]{prop:order}
(1) Messages sent with \snd{} by the same actor $\iota_a$ to the same receiver $\iota_b$
start turns of $\iota_b$ in the order $\iota_a$ sent them. Nothing is claimed about the
relative order of messages from different senders. (2) A \fs{} from $\iota_a$ to $\iota_b$ is never placed in $\iota_b$'s mailbox: its
turn starts when a \fs{} rule applies, whatever the mailbox holds, so it can start before
messages already queued for $\iota_b$, including earlier \snd{}s from $\iota_a$. While
$\iota_b$ is busy, the calculus leaves open whether the pending call or the head of the
mailbox starts next; a runtime that always prefers a pending \fs{} guarantees that the
call starts before every message that was in $\iota_b$'s mailbox when it was made.
(3) Messages sent during the callee's turn of a \fs{} are enqueued before any message the
caller sends after the \fs{} returns.
\end{proposition}
\begin{proof}
(1) The sends of $\iota_a$ are totally ordered, because $\iota_a$ has at most one frame
(\cref{lem:oneframe}); \textsc{Send} appends and \textsc{Receive} removes the head. (2) The \fs{} rules start
the callee's turn without consulting its mailbox, and \textsc{Receive} does not consult
pending calls; when both are enabled for $\iota_b$ the choice is free. Under the
preference, each time $\iota_b$ becomes idle while the call is pending, a \fs{} rule is
applied to $\iota_b$ before any \textsc{Receive} of $\iota_b$, so no queued message of
$\iota_b$ starts first. (3) The caller's frame is waiting from
the \fs{} until \textsc{Fast-Return}, and the callee's sends happen before that.
\end{proof}

Part (2) is the formal counterpart of the statement that \fs{} bypasses the mailbox, and
it is one of the practical motivations for \fs{}: a call is not delayed by a backlog in
the callee's mailbox. It is not a priority mechanism, since a turn in progress is never
interrupted (\cref{rem:notprovided}). Neither runtime in \kh{} implements the preference.
The CPU runtime's \fs{} acquires a plain \texttt{std::mutex}, which imposes no order
between a waiting \fs{} and the receiver's next mailbox message. On the FPGA, \fs{} is an
inline call within a group, so its callee can be busy only on the caller's own call
chain.

\subsection{\fs{} is not send-then-wait}
\label{sec:notsw}

A synchronous call is commonly implemented as a send followed by a blocking wait for the
reply, and the classic results show that synchronous communication can always be encoded
in this way. We show that the two are not interchangeable once actors share a thread:
there is a program in which the send-then-wait version never completes and the \fs{}
version does. This is the formal justification for treating \fs{} as a primitive in its
own right rather than as a pattern built from \snd{}.


Let \emph{send-then-wait} denote the pattern of the first group in
Section~\ref{sec:related-sync}: the caller sends a request with \snd{} and its frame then
blocks until a reply message for it arrives. We model the blocking by a frame that no rule
reduces until the reply has been enqueued in the caller's mailbox; the frame stays on its
thread.

\begin{proposition}[Shared resources]
\label[proposition]{prop:notsendwait}
Let actors $\iota_a$ and $\iota_b$ share a home thread, and let $\iota_b$'s method return
without further communication. A turn of $\iota_a$ that obtains $\iota_b$'s result by
send-then-wait never completes. The same turn using \fs{} with \textsc{Fast-Local}
completes.
\end{proposition}
\begin{proof}
With send-then-wait, the request is enqueued in $\iota_b$'s mailbox and $\iota_a$'s frame
stays on the shared thread $\theta$. \textsc{Receive} for $\iota_b$ requires $\theta$ to
have an empty stack, which it never has again, so the reply is never produced. With \fs{},
\textsc{Fast-Local} pushes $\iota_b$'s turn on $\theta$ above $\iota_a$'s frame; it
terminates and \textsc{Fast-Return} resumes $\iota_a$.
\end{proof}

\Cref{fig:deadlock}(b) illustrates the proposition. The encodings of synchronous into asynchronous communication
\cite{hondatokoro1991,boudol1992} are sound in a setting in which every process
progresses independently. In a setting with a bounded number of execution resources
(actor groups, ABS cogs, E vats, one pinned thread per core, a fixed number of FPGA
processes), \fs{} and send-then-wait differ in whether they complete. The proposition
also explains why a synchronous call within one scheduling unit, as in ABS cogs and E
vats, must execute on the caller's processor: within the unit, send-then-wait cannot
complete.

% ---------------------------------------------------------------
\section{Simulation and debugging from a global queue}
\label{sec:debug}
% ---------------------------------------------------------------

Deterministic replay executes recorded external inputs through the same actor handlers
that are used in production; in a trading system this is a backtest. A debugger requires
the same facility together with the ability to stop, step and inspect. Both are simplest
to provide when every actor in the system, regardless of its implementation language and
of the substrate on which it normally runs, is driven from a single queue by a single
thread: every message is enqueued there, receivers dequeue their messages from it, and
the execution is a single deterministic sequence that can be replayed, paused and
inspected. The \kh{} actor group, which co-schedules actors behind one mailbox, already
serves as such a simulator for CPU actors \cite{mayeski2026fastsend}. The question
is whether \fs{} preserves the correspondence between this simulator and the concurrent
system.

The answer has two parts, which determine the structure of the section. A simulator is
useful for finding bugs if every behaviour it exhibits can also occur in the real
system; otherwise a failure observed in simulation may be an artefact of the simulator.
It is useful for excluding bugs only if, in addition, every behaviour of the real system
also occurs in simulation. Section~\ref{sec:gq-sem} defines the simulator and the real
system as two variants of the calculus. Section~\ref{sec:gq-sound} proves the first
property in the presence of \fs{}. Section~\ref{sec:gq-incomplete} shows that the second
property fails, identifies the behaviour the simulator misses, and gives an offline check
for its most important instance, deadlock.

\subsection{The global-queue semantics}
\label{sec:gq-sem}

To compare the simulator with the real system, we describe both as instances of the
calculus of Section~\ref{sec:calculus} with different resources. The simulator has a
single thread and a single queue shared by all actors. The real system, which we call
the production semantics, has any number of threads, a mailbox per actor, and either form
of \fs{} at each call site. The comparison requires one condition on the real system; we
state it below and identify the runtimes in this paper that satisfy it.

The global-queue semantics $\mathit{GQ}$ is the calculus of Section~\ref{sec:calculus}
with one thread $\theta_0$, the home thread of every actor, and with per-actor mailboxes
replaced by one FIFO queue $Q$ of pairs $(\iota_b, m)$:
\begin{itemize}[leftmargin=1.4em]
  \item \textsc{Send} appends $(\iota_b, \Msg{msg, \pass(\overline{v})})$ to $Q$;
  \item \textsc{Receive-GQ}: when $\theta_0$ has an empty stack, remove the head
  $(\iota_b, m)$ of $Q$ and start $\iota_b$'s turn for $m$;
  \item \fs{} uses \textsc{Fast-Local} on $\theta_0$.
\end{itemize}
An actor that normally runs on another substrate participates through its method bodies
alone: an FPGA actor's turn is its step function, executed by the simulator in software;
a Rust actor's turn is its handler, invoked across the language boundary. By receiver
transparency, the body is the same regardless of how the turn is started.

The production semantics $\mathit{P}$ is the calculus of Section~\ref{sec:calculus} with
any assignment of actors to threads and any choice of \textsc{Fast-Local} or
\textsc{Fast-Remote} per call site, subject to one condition on the resources that
\textsc{Fast-Remote} uses:

\begin{assumption}[Dedicated remote resources]
\label[assumption]{ass:dedicated}
A thread that serves as the home thread of a \textsc{Fast-Remote} callee is the home of
that actor only.
\end{assumption}

The runtimes considered in this paper stand in the following relation to the assumption.
\begin{itemize}[leftmargin=1.4em]
  \item \emph{Within the CPU runtime, and within an FPGA group}: \fs{} is
  \textsc{Fast-Local}, so the assumption does not apply.
  \item \emph{Between FPGA processes, and across PCIe}: \kh{} offers no \fs{}; a request
  and its reply are two \snd{}s, and the assumption does not arise.
  \item \emph{Another machine}: the assumption holds if the remote
  actor has a dedicated thread, and fails if that thread also serves other actors, for
  example a group.
\end{itemize}
Where the assumption fails, \cref{thm:gqsound} does not cover the calls concerned.

\subsection{Soundness}
\label{sec:gq-sound}

We prove that the simulator exhibits no behaviour of which the real system is incapable.
The proof replays a simulator run in the real system step by step and checks that each
step of the simulator is also permitted in the real system. The only non-trivial case is
a \fs{}: in the simulator the callee is always idle when called, unless it is already on
the current call chain, and we must show that the real system can also find it idle.

Two executions \emph{agree} if every actor starts the same turns in the same order, with
$\alpha$-equivalent messages, and every turn ends with an $\alpha$-equivalent value and
heap.

\begin{theorem}[Trace soundness of the global queue]
\label{thm:gqsound}
Under \cref{ass:dedicated}, for every finite execution of $\mathit{GQ}$ from a given
initial configuration there is an execution of $\mathit{P}$ from the corresponding initial
configuration that agrees with it: the traces of $\mathit{GQ}$ are included in those of
$\mathit{P}$. In particular, a configuration in which a turn can no longer progress, or
an error state, reached in $\mathit{GQ}$ has an agreeing counterpart in $\mathit{P}$.
\end{theorem}
\begin{proof}
We build the $\mathit{P}$ execution step by step, maintaining the invariant that at every
point where $\theta_0$ has an empty stack in $\mathit{GQ}$, every thread of $\mathit{P}$
has an empty stack, the heaps agree, and each actor's mailbox in $\mathit{P}$ is the
projection of $Q$ onto that actor, in order.

\emph{Receive.} $\mathit{GQ}$ takes the head $(\iota_b, m)$ of $Q$. By the invariant,
$m$ is the head of $\iota_b$'s mailbox in $\mathit{P}$, since every earlier pair for
$\iota_b$ in $Q$ has already been removed. $\iota_b$'s home thread is idle and $\iota_b$
is not busy, so \textsc{Receive} applies in $\mathit{P}$ to the same message.

\emph{Within a turn.} $\mathit{P}$ reduces only the thread that holds the corresponding
frame, mirroring each $\mathit{GQ}$ step: actor-local steps are identical; \textsc{Send}
appends to the receiver's mailbox, which preserves the projection invariant.

\emph{\fs{}.} In $\mathit{GQ}$, \textsc{Fast-Local} to $\iota_b$ applies if and only if
$\iota_b$ has no frame on $\theta_0$'s stack. In the mirrored $\mathit{P}$ execution the
only frames in existence are the ones mirroring that stack, so $\iota_b$ is busy in
$\mathit{P}$ exactly when it is busy in $\mathit{GQ}$. If $\mathit{P}$ uses
\textsc{Fast-Local} for the call, it applies. If it uses \textsc{Fast-Remote}, the rule
also needs $\iota_b$'s home thread to be idle. By \cref{ass:dedicated} a frame reaches
that thread only as a turn of $\iota_b$ or stacked above one; $\iota_b$ has no frame, so
the thread is idle. The callee's turn then
proceeds as above, and \textsc{Fast-Return} applies in both.

If a $\mathit{GQ}$ frame is blocked on a \fs{} to a busy actor, the mirrored
$\mathit{P}$ frame is blocked on the same actor. Agreement of values and heaps follows from
\cref{thm:determinism}, since the mirrored turns receive the same replies.
\end{proof}

\begin{corollary}[What the simulator shows is real]
Every value a \fs{} returns in $\mathit{GQ}$, every assertion failure, error state or
same-thread \fs{} cycle it reaches, can occur in the concurrent system. A $\mathit{GQ}$
run is deterministic given its inputs, so it can be replayed exactly.
\end{corollary}

The global-queue simulation is therefore sound in the presence of \fs{}. The argument
rests on the fact that in a single-threaded run the callee of a \fs{} is idle unless it
is already on the current call chain: the simulator takes only the branch of \fs{} in
which the callee is idle, which is one of the branches available to the concurrent
system. This does not hold in general: without \cref{ass:dedicated}, a
\textsc{Fast-Remote} callee whose resource is occupied by another actor blocks in
$\mathit{P}$ where $\mathit{GQ}$ proceeds, and the simulator would then exhibit behaviour
that the concurrent system cannot produce.

\subsection{What the simulator cannot show}
\label{sec:gq-incomplete}

A simulator that executes one handler at a time cannot reproduce behaviour that requires
two handlers to be in progress simultaneously. We give two such behaviours, one of which
is a deadlock, and thereby show that the simulator is sound but not complete: a bug it
exhibits is real, but a bug-free run does not establish the absence of bugs. For
deadlock, the most important case, we then give a check that is independent of the
inputs exercised: the graph recording which actors can \fs{} which must be acyclic.

\begin{proposition}[Incompleteness]
\label[proposition]{prop:gqincomplete}
There are executions of $\mathit{P}$ that agree with no execution of $\mathit{GQ}$. Two
examples: (1) the deadlock of \cref{fig:deadlock}(a), where the turns of $X$ and $Y$,
both started from mailboxes, never end; (2) a turn of $\iota_a$ that sends $m$ to
$\iota_b$ and then makes a \fs{} to $\iota_b$, where $\iota_b$'s home thread runs the turn
for $m$ before the \fs{} applies, so the call sees $\iota_b$'s state after $m$.
\end{proposition}
\begin{proof}
In $\mathit{GQ}$, \textsc{Receive-GQ} needs an empty stack, so at most one turn started
from a mailbox is unfinished at any time, and every other turn in progress is a \fs{}
callee on the same stack. (1) has two unfinished turns started from mailboxes, so an
agreeing $\mathit{GQ}$ execution would need both, which it cannot have. In (2), $m$ enters
$Q$ during $\iota_a$'s turn and can start only after that turn ends, so in every
$\mathit{GQ}$ execution $\iota_b$ starts the turn for the \fs{} before the turn for $m$;
in the $\mathit{P}$ execution it starts them in the other order.
\end{proof}

The incompleteness extends beyond executions in which two turns overlap. The
global-queue semantics has a single thread, a single FIFO queue and, at each point, at
most one applicable rule up to the choice of fresh names, so it admits no scheduling
choice at all.

\begin{proposition}[The global queue is deterministic]
\label[proposition]{prop:gqdet}
From a given configuration, $\mathit{GQ}$ has exactly one maximal execution up to
$\alpha$-equivalence. In particular, for the counter of
\cref{prop:unbounded-send,prop:unbounded-fs}, $\mathit{GQ}$ yields one final value of
$x$, whereas $\mathit{P}$ yields every value in an infinite set.
\end{proposition}
\begin{proof}
Every rule of $\mathit{GQ}$ applies either to the top frame of $\theta_0$, where the
actor-local rules, \textsc{Fast-Local}, \textsc{Fast-Return} and \textsc{Turn-End} are
mutually exclusive and evaluation contexts fix the redex, or, when the stack of
$\theta_0$ is empty, to the head of $Q$ by \textsc{Receive-GQ}. Hence at most one rule
applies to any configuration, and its result is unique up to the fresh names chosen by
\textsc{Spawn} and \fs{}. For the counter of \cref{prop:unbounded-send} with
$Q = (c, \mathtt{go})\cdot(b, \mathtt{start})$, the unique execution receives \texttt{go},
\texttt{start}, \texttt{go}, \texttt{stop} and a final \texttt{go}, which has no effect,
in that order, and ends with $x = 2$.
\end{proof}

A replay therefore exhibits one interleaving of the concurrent system, the one fixed by
the order in which messages enter $Q$. Behaviours that depend on a different relative
speed of threads, such as every other final value of the counter, are absent from
simulation even when no two turns overlap; \cref{prop:gqincomplete} does not cover them,
and testing in simulation does not exclude them.

provide. Replay can therefore confirm bugs but cannot exclude the two classes above. The
first can be addressed offline.

\begin{proposition}[Cycles in the call graph]
\label[proposition]{prop:callgraph}
Let $G$ be the directed graph on actors with an edge $\iota_a \to \iota_b$ whenever some
turn of $\iota_a$ can evaluate a \fs{} to $\iota_b$. If $G$ is acyclic, no execution of
$\mathit{P}$ reaches a wait-for cycle.
\end{proposition}
\begin{proof}
The frames on any thread, bottom to top, belong to a path in $G$, since each frame above
the bottom one was pushed by a \fs{} from the frame below (\textsc{Fast-Local}); a
\textsc{Fast-Remote} callee's frame extends the same path onto another thread. A wait-for
edge $\theta \to \theta'$ adds the edge from the actor on top of $\theta$ to an actor
already on the path held by $\theta'$. Following a wait-for cycle and concatenating these
paths yields a cycle in $G$.
\end{proof}

A $\mathit{GQ}$ run can record the \fs{} edges it executes. The recorded graph is the
subgraph of $G$ containing only the calls exercised by the inputs, so a cycle in it is a
genuine hazard to be removed, whereas the absence of a cycle is evidence only for the
paths covered by the backtest. A static analysis of the call sites would yield the whole
of $G$.

\paragraph{Time.} $\mathit{GQ}$ reproduces the events of an execution but not their
timing. Latency on each substrate is a separate question (Section~\ref{sec:future}).

\section{Mapping \snd{} and \fs{} onto substrates}
\label{sec:substrates}
% ---------------------------------------------------------------

We now consider the model when actors execute on concrete hardware: CPU threads, a Rust
runtime, an FPGA and, as a proposal, a GPU. The calculus specifies the meaning of \snd{}
and \fs{}; each substrate must provide a mechanism with that behaviour. We argue that,
with \fs{} in the model, every substrate has a direct mechanism for each primitive, and
that on an FPGA \fs{} is what makes the mapping complete.

An FPGA design is composed of two kinds of connection. Independent hardware processes
execute concurrently and exchange data through FIFOs. Within one process, computations
are fused into a single pipeline in which the output of one stage feeds the next
directly, without a FIFO or a handshake; this is how FPGA designs attain their latency
and throughput. Actors map onto processes and \snd{} onto FIFOs. Fused logic, however,
has no counterpart in a model with asynchronous send alone, and it cannot be given one
by constructing request/reply from \snd{}: two actors fused into one process share that
process, and \cref{prop:notsendwait} shows that a send followed by a wait between actors
that share their execution resource never completes. With \fs{}, a call between fused
actors is the callee's handler inlined into the caller's pipeline. A call to another
process would be a \snd{} followed by a blocking wait, which is the cost \fs{} is
intended to avoid, so the runtime does not offer it: \fs{} is confined to one process,
and this restriction is checked when the design is built. Each of the two connections
offered by the hardware then corresponds to a primitive of the model: the FIFO to
\snd{}, the fused pipeline to \fs{}.

The calculus leaves open what a thread is and how a mailbox is implemented. Each
substrate supplies both, together with a distinct mechanism for each primitive
(\cref{tab:mapping}).

On an FPGA the two \fs{} rules correspond to two distinct hardware arrangements. When the
callee is compiled into the caller's hardware process, its handler becomes part of the
caller's pipeline and executes on the caller's resource: \textsc{Fast-Local}. When the
callee is a separate process, it has its own resource, on which the caller would wait:
\textsc{Fast-Remote}. The runtime described in Section~\ref{sec:impl} implements only the
first: a process is one actor or a group of actors, \textsc{Fast-Local} applies between
members of a group, and actors in different processes communicate only by \snd{}.

The same pattern holds on every substrate. \snd{} is a queue between two independently
scheduled resources. \fs{} is either an inline call on the caller's resource, where the
substrate permits one resource to execute another actor's handler, or a blocking request
to a resource dedicated to the callee, where it does not. The calculus of
Section~\ref{sec:calculus} covers both cases with a single semantics, and
\cref{thm:isolation,thm:determinism,thm:liveness} hold for any mixture.

In the model, a \fs{} is possible between any two substrates on which the caller can
wait: a CPU thread can wait on a condition, and an FPGA process on a blocking stream
read. In \kh{} no \fs{} crosses a substrate boundary. Across PCIe it would amount to a
\snd{} followed by a blocking wait of a microsecond or more, so a request and its reply
are two \snd{}s \cite{fpgaactors}.

\section{Practical implementation in \kh{}}
\label{sec:impl}
% ---------------------------------------------------------------

\kh{} provides actors on three runtimes (C++ on CPU threads, Rust, and an FPGA runtime
\cite{fpgaactors}), and a GPU runtime is planned. Each runtime has its own actors,
written in its own language; an actor is not recompiled from one runtime to another. The
runtimes share the model: on every runtime an actor holds references to other actors,
whether on the same runtime or on another, and uses the same two primitives, \snd{} and
\fs{}, and the same \texttt{reply}. The extended actor model of
Sections~\ref{sec:calculus} and~\ref{sec:properties} is the semantics of each runtime and
of any combination of them, with each \fs{} implemented by \textsc{Fast-Local} as
\cref{tab:mapping} shows. \Cref{tab:status} distinguishes what is formalised, what is
implemented, and how each part has been exercised. The remainder of this section
describes each runtime and then the debugging and simulation facility.

\paragraph{CPU runtime.} The \kh{} C++ runtime \cite{mayeski2026fastsend} implements
actors with a mutex-protected turn, a selectable mailbox per actor, \snd{}, \fs{} and
groups. \fs{} acquires the callee's lock on the caller's thread and executes its handler
inline; a reply is returned as a value. The delivery flag is private to the framework,
but some message fields (the queue depth, the ``mailbox empty'' flag and the
destination) are set differently under the two deliveries, so a handler that reads them
can infer how it was invoked. Receiver transparency in \kh{} is therefore a property of
how handlers are written, as in \cref{rem:transparency}, rather than one enforced by the
framework. A mailbox may also be configured to busy-poll instead of sleeping, which
changes the cost of \snd{} between threads but not its semantics.

\paragraph{Rust runtime and interop.} A separate Rust actor runtime hosts Rust actors.
C++ and Rust actors address each other through C-ABI bridges generated from a single
message schema; both \snd{} and \fs{} operate across the boundary; a cross-language \fs{}
delivers the message and returns no value.

\paragraph{FPGA runtime.} The FPGA runtime, \texttt{kfpga}, is written in C++ for Vitis
HLS and described in \cite{fpgaactors}. A process, which is either one actor or a group
\texttt{kfpga::Group<A,B,\ldots>}, is an always-running \texttt{hls::task}, and its
handlers are a switch on the message identifier. An actor reference is a port number and
an actor id, fixed when the design is built; a port is one end of a link, a FIFO each
way, and there are no routers. \snd{} is one write into a FIFO. \fs{} is an inline call
between members of one group, and a \fs{} to an actor outside the group does not compile.
In each step, a process serves the group's own queue first and then its ports in turn.
On the CPU, an FPGA actor is addressed through a proxy that offers only \snd{}; the card
writes into lanes in host memory that the receiving thread's own mailbox polls, so no
host thread routes messages. The designs pass C simulation, synthesis and RTL co-simulation,
and the MDP3 handler is placed and routed at 250~MHz on the Alveo X3522PV's device.

\paragraph{GPU runtime.} The same structure maps onto a GPU: actors as warps or thread
blocks of a persistent kernel, mailboxes as device-memory rings, \fs{} inside the kernel as
a device function call, and a host bridge over rings in pinned memory. This is a
proposed mapping.

\paragraph{Global queue and sequencer.} Debugging and simulation across runtimes are to
be provided by a global queue and a \emph{sequencer}, which implement the global-queue
semantics $\mathit{GQ}$ of Section~\ref{sec:debug}. In this mode every runtime
passes each message it sends, whatever its destination, to the sequencer instead of
delivering it. The sequencer assigns the message a global sequence number and appends it
to the global queue. It then delivers messages one at a time: it removes the head of the
queue, passes it to the runtime of the receiving actor, and waits until that runtime
reports the end of the turn, including every \fs{} made during the turn, before
delivering the next. Each runtime therefore requires only an adapter with two
operations, accepting a delivery and reporting the end of a turn, and retains its own
actors, handlers and \fs{} mechanism unchanged; an FPGA actor can be driven either on the
card or in a software simulation of its hardware process.

Because deliveries are serialized, a debugger can step through the queue one message at a
time and display, before each step, which actor on which runtime executes next and with
which message; between steps it can inspect the state of any actor on any runtime, and it
can break on a given actor, message type or runtime. \Cref{thm:gqsound} gives this
facility its value for every call that satisfies \cref{ass:dedicated}: the sequence the
debugger displays is one that the concurrent system can produce, so a fault found by
stepping is genuine. The same sequence, when recorded, replays a backtest exactly, and the
\fs{} calls it executes yield the call graph of \cref{prop:callgraph}. The sequencer
cannot exhibit behaviour such as that of \cref{prop:gqincomplete}, which requires more
than one turn started from a mailbox to be in progress simultaneously.

\section{Related work}
\label{sec:related}
% ---------------------------------------------------------------

\paragraph{Actor semantics.} The operational semantics of Agha, Mason, Smith and Talcott
\cite{agha1997} and the four-family semantics of De Koster and De Meuter
\cite{dekoster2024} contain only asynchronous communication. We extend the latter, and
state our isolation and liveness results relative to its isolated turn principle.

\paragraph{Synchronous calls.} ABCL/1 \cite{yonezawa1986} and ABS \cite{johnsen2012abs}
provide synchronous calls between concurrent objects that block the caller while the
callee runs on its own processor, and ABS adds reentrant synchronous calls inside a cog.
E \cite{miller2005} restricts immediate calls to one vat. Extended Rebeca
\cite{sirjani2005extended,sirjani2005jucs} is the closest actor language with a formal
semantics for synchronous messages, and differs from \fs{} in each respect listed in
\cref{tab:sync}. Its synchronous messages are rendezvous: the receiver must execute an
explicit \texttt{receive} statement, no handler is invoked, and data flows only from
sender to receiver, so there is no reply value. They are confined to one component,
whereas \fs{} addresses any actor. A rebec blocked in a rendezvous is blocked inside a
method, whereas the turn of a \fs{} callee is an ordinary handler that runs to
completion. The semantics of Extended Rebeca has no execution resources, so the
following questions addressed here for \fs{} do not arise in it: behaviour when the
callee's resource is shared (\cref{prop:notsendwait}) or occupied (\cref{ass:dedicated}),
and single-queue simulation (Section~\ref{sec:debug}). Its aim is compositional model
checking.
We therefore do not claim novelty for synchronous messages in actor languages; the
contribution is the particular resource-sensitive primitive and its properties.

Consider an encoding of \fs{} by rendezvous. The callee would wait at a
\texttt{receive} for the request, execute the handler's code, and return the result
through a second rendezvous. The callee's code then executes on the callee's side rather
than on the caller's resource, and the caller's blocked computation retains its resource
while it waits; when the two share one resource, the argument of \cref{prop:notsendwait}
applies unchanged, and the encoding deadlocks where \textsc{Fast-Local} completes. The
survey of active-object languages by De Boer et al.
\cite{deboer2017survey} maps this design space.

\paragraph{Encodings.} Honda and Tokoro \cite{hondatokoro1991} and Boudol
\cite{boudol1992} encode synchronous in asynchronous communication; \cref{prop:notsendwait}
locates where such encodings stop applying once resources are bounded.

\paragraph{Actors on hardware.} CAL and the StreamBlocks compiler
\cite{bezati2021streamblocks} compile dataflow actors to both CPUs and FPGAs. Dataflow
actors fire on token availability and have no synchronous call; our FPGA runtime targets
the message-passing actor model with both primitives.

% ---------------------------------------------------------------
\section{Open problems}
\label{sec:future}
% ---------------------------------------------------------------

\begin{itemize}[leftmargin=1.4em]
  \item A mechanisation of the calculus and proofs, for instance by extending the PLT
  Redex models of \cite{dekoster2024}.
  \item The calculus has no failures; a \fs{} to an actor on a failed resource waits
  indefinitely. Timeouts and their interaction with isolation remain open.
  \item The mailboxes of the calculus are unbounded, so \snd{} never blocks and never
  loses a message. In hardware, the FIFOs between FPGA processes have a fixed depth, and a
  write into a full FIFO waits; two processes that send to each other can then both wait
  indefinitely. A \snd{} between members of one group that finds the group's queue full is
  dropped and counted. Across PCIe a CPU \snd{} never waits; envelopes queue at the CPU
  end of the link \cite{fpgaactors}. \Cref{thm:liveness} does not cover the blocking,
  and the calculus does not model the loss. Modelling bounded mailboxes, and sizing FIFOs
  so that a design cannot reach it, remain open.
\end{itemize}

% ---------------------------------------------------------------
\section{Conclusion}
% ---------------------------------------------------------------

We have proposed extending the actor model with a synchronous send, \fs{}, as a second
primitive alongside asynchronous send: the caller waits while the receiver handles the
message and obtains the reply as the return value. We gave \fs{} a formal semantics with
explicit execution resources and proved three properties of the extended model.
Isolation holds. Determinism holds relative to the replies a handler receives. Liveness
is conditional: under terminating handlers and fair scheduling, a handler can block only
on a cycle of \fs{} calls, and without \fs{} the original guarantee holds. When actors
share a thread, \fs{} completes where a send followed by a wait deadlocks; \fs{} is
therefore a primitive in its own right rather than a pattern built from \snd{}. A single
global queue remains a sound simulator in the presence of \fs{}: replay, or a debugger
that executes every actor, in any language and on any substrate, from one queue, exhibits
only behaviour that the concurrent system can produce, though not all such behaviour.

With \fs{} in the model, actors map directly onto hardware. On an FPGA, \snd{} is a FIFO
between hardware processes and \fs{} is logic fused into one process, realised as an
inline call between the actors of one group; actors fused into one process can call each
other only with \fs{}. The same two mechanisms, a queue and an inline or blocking call,
implement the two primitives on CPU threads and in the Rust runtime, and a GPU runtime
would follow the same pattern.
