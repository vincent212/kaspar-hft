# Feed description: LMAX Exchange post-trade (Broker Trading FIX 4.4)

Not certified. Short names as in `../../order_entry/lmax/feed.md`: TR is LMAX's
Broker Trading `fix-spec.json` (FIX.4.4 version, release 370, 2023-12-02); DC the
MTF Drop Copy `fix-spec.json` (2.7, 2023-03-13). JSON documents have no pages;
cited by heading, message and field.

## 1. Venue and documents

LMAX's broker service has no separate drop-copy or trade-capture session. The
Broker Trading API carries both post-trade sources this client uses:

| Source | Messages | TR |
|---|---|---|
| execution reports on the order session | ExecutionReport (8) with ExecType F (Trade), G (TradeCorrect), H (TradeCancel) | ExecutionReport, field 150 |
| trade capture on a trading session | TradeCaptureReportRequest (AD), TradeCaptureReportRequestAck (AQ), TradeCaptureReport (AE) | prologue, Application Recovery; messages AD, AQ, AE |

The MTF Drop Copy service (DC) is for MTF members, configured by LMAX Market
Operations, and has no demo host in CG; it is not used. DC is cited below only
where it says something about identifiers or units that TR does not.

## 2. Transport

As the order session (`../../order_entry/lmax/feed.md` section 2): TLS to
`fix-order.london-demo.lmax.com:443` on demo, FIX 4.4, Username and Password on
the Logon. Whether a second, concurrent session for the same user is allowed is
not stated (section 10, item 3); the client works with or without one.

## 3. Framing

FIX 4.4 through QuickFIX with the dictionary generated from TR
(`../../order_entry/lmax/dict/LMAX-FIX44-Trading.xml`).

## 4. Message catalogue

The tables for AD, AQ, AE and 8 are in `../../order_entry/lmax/feed.md`
section 4. Fields this client reads:

| Message | Fields | TR |
|---|---|---|
| AD (sent) | TradeRequestID 568 (at most 16 characters, unique while active), TradeRequestType 569 = 1, SubscriptionRequestType 263 = 1 (snapshot and updates), Account 1, NoDates 580 with TransactTime 60 (start of the trading day) | AD |
| AQ | 568, 569, 263, TotNumTradeReports 748 (only when 0 trades), TradeRequestResult 749 (0, 99), TradeRequestStatus 750 (0 accepted, 2 rejected), Text 58 | AQ |
| AE | 568, LastRptRequested 912, ExecID 17, SecondaryExecID 527, SecurityID 48, LastQty 32, LastPx 31, TradeDate 75, TransactTime 60, NoSides 552 (Side 54, OrderID 37, ClOrdID 11, Account 1), commission 12, 13, 479 | AE |
| 8 | ExecType 150, ExecID 17, SecondaryExecID 527, OrderID 37, Side 54, SecurityID 48, LastQty 32, LastPx 31, TransactTime 60, SettlDate 64, Account 1 | ExecutionReport |

TR's dictionary has no TradeCaptureReportAck (AR); none is sent.

## 5. Sequencing and recovery

- On every logon of its own session the client requests matched trades from the
  start of the current trading day (17:00 New York, section 6) with updates. The
  day's replay is applied to the ledger, which drops what it holds.
- The order manager forwards every Trade, TradeCorrect and TradeCancel report
  (`ExecCopy`), including resends; the ledger drops repeats.
- PossDupFlag (43) is passed on in `poss_dup` for information.
- The ledger is cleared when a logon falls in a new trading day.

## 6. Semantics

| Item | Reading | Source |
|---|---|---|
| Report lifecycle | AE: one per trade (no TradeReportTransType, TradeReportType or TradeReportID in TR's AE); 8: F new trade, G correction, H cancel | TR AE, 150 |
| Trade identifier | (OrderID, SecondaryExecID); ExecID when SecondaryExecID is absent or "0" | TR 17, 37, 527; DC (below) |
| Correction and cancel linkage | by the same (OrderID, SecondaryExecID) | none in TR (no ExecRefID) |
| Side | NoSides in AE; Side in 8; the firm's own side | TR |
| Trading day | starts 17:00 New York; TradeDate is "local time at place of trade" | TR 75; session schedule 17:02 |
| Settlement | SettlDate on 8 only when LMAX enables it | TR changelog release 120 |
| Counterparty | not given | TR |

DC says, of the MTF drop copy: "The ExecID (17) is the unique identifier for each
LMAX trade and can be used to reconcile trades with executions received on the
client's Order Entry FIX sessions"; and recommends ExecID with Side as the key, to
separate the two sides of a self-match. TR defines the broker ExecID as the id of
the execution message, "unique over all time", and SecondaryExecID as "the
execution ID as generated by the MTF". The reading taken is that the broker
SecondaryExecID is the trade id DC calls ExecID; OrderID in the key separates the
two sides of a self-match as Side does in DC.

## 9. Pitfalls

`pitfalls.md` section 7:

- FIX version: FIX 4.4 (TR); not FIXT.
- Custom tags and groups: LMAX's dictionary generated from TR; unknown tags
  accepted (TR Compatibility).
- Credentials: on the Logon (TR Logon); no UserRequest.
- A missing field throws into QuickFIX: the session catches everything in
  `fromApp`; a report that does not parse is counted, never rejected to LMAX.
- Requests before a session status message: TR has no such message.
- Subscription: TradeRequestType 1 (matched trades, the only value),
  SubscriptionRequestType 1, from the start of the trading day; the Ack's
  status 2 is logged and counted.
- Report lifecycle: AE has no TradeReportTransType; G and H on 8 have no
  reference to the trade they change (section 10, item 2).
- Duplicates on reconnect: the day's replay and resends; idempotent through the
  ledger (`ReconnectReplayAddsNothing`, `ReportsReachTheSubscriberOnce`).
- Price versus yield, accrued interest: not applicable (spot FX).
- Daily sequence reset: the client's own session resets with the trading
  gateway's weekly schedule; the ledger is cleared per trading day.
