# Design: an agent that builds Kaspar feed handlers from exchange specifications

## Purpose and scope

Connecting kaspar-hft to a new venue means writing a feed handler: code that turns
the venue's bytes into Kaspar messages. The work is repetitive in structure and
treacherous in detail. This design describes an agent, packaged as a Claude Code
skill in this repository (`.claude/skills/build-feed-handler/`), that takes a
venue's specification and produces the handler.

Two kinds of handler are in scope:

| Kind | Input | Output |
|---|---|---|
| **Market data** | multicast (with A/B feeds), TCP, WebSocket or FIX market-data sessions; binary (SBE, ITCH, PITCH, fixed-offset), FIX tag-value or JSON encodings | normalized order-book records (`bfile::l3_t`: MBO, trades, end of packet, gap, channel reset) sent to OB; price-level feeds pass through `Mbp2Mbo` |
| **Post-trade** | FIX drop-copy and trade-capture sessions (`TradeCaptureReport`), proprietary post-trade feeds | normalized trade-capture messages for position keeping and STP publication |

The agent delivers the handler actors, their tests, and a live connectivity check
run once the user supplies credentials. It is not expected to deliver a
production-ready handler unaided: a person reviews the agent's reading of the
specification and finishes the handler.

## Why the problem is tractable

The task is bounded because the output is a set of Kaspar actors with a fixed
contract. An agent asked to "write a market-data handler" has no definition of done;
an agent asked to "produce actors that turn this venue's messages into these
records" has a fixed interface, working examples of every transport class, and a
standard form of test.

| Existing handler | Class it demonstrates |
|---|---|
| CME MDP3 (`mdp3/`, codecs generated by `genschema/` from CME's SBE XML) | binary multicast, A/B arbitration, snapshot recovery, MBO |
| Binance (`sim/src/BinanceFeed.cpp`, `BinanceSync.cpp`) | WebSocket JSON, REST snapshot plus diff stream, gap detection |
| Coinbase (`CoinbaseFeed`, `CoinbaseSync`) | WebSocket with full-book snapshot and per-connection sequence numbers |
| Hyperliquid (`HyperliquidFeed`, `HyperliquidSync`) | periodic whole-book snapshots, diffed |
| TT order routing (`ttom/`) | FIX session over QuickFIX |
| m2 Fenics and Dealerweb handlers (private repository) | fixed-offset binary messages generated from a hand-extracted field table (`*_def.txt` + `msg_gen.py`) |
| m2 post-trade clients (private repository) | FIX 4.4 and FIX 5.0 SP2 `TradeCaptureReport` over QuickFIX |

Each actor can be tested in isolation: a test sends it input and checks the
records it emits (`unit_test/src/test_crypto_sync.cpp`). The OB, the simulator,
`compare_books.sh` and the `--dump` monitors provide further checks without new
code.

## Inputs

1. **The specification.** PDFs (often several hundred pages), and machine-readable
   artefacts where they exist: SBE XML templates, FIX data dictionaries (QuickFIX
   XML), JSON or protobuf schemas.
2. **Sample data**, where available: packet captures, vendor data, the venue's
   sample files, or live public endpoints.
3. **A reference**, where available: the venue's own decoder, vendor-normalized
   data, or (for crypto venues) REST snapshots of the book.
4. **Credentials and network access** for the live check, supplied by the user at
   the end.

Specifications and data under NDA are read locally and never committed to this
public repository; the feed description and generated code for such a venue are
written to the user's private repository.

## Workflow

| Step | Performed by | Result |
|---|---|---|
| 1. Extract the specification into a feed description | subagents, one per part of the specification | `feed.md`: transport, framing, message catalogue, sequencing and recovery, book or trade semantics, mapping to Kaspar messages, every entry citing its page and section |
| 2. Review the feed description | **the user** | approved description; every item the agent marked *ambiguous* is resolved |
| 3. Generate decoders | a deterministic generator where a schema exists (SBE XML, FIX dictionary, a field table); a subagent otherwise | message structs and decode functions |
| 4. Write the handler actors | a subagent, starting from the nearest existing handler | feed actor, sync and recovery logic, instrument loader, configuration |
| 5. Test | a subagent | unit tests from the specification's examples and from samples; replay with invariants; gap and reset injection; comparison with a reference where one exists |
| 6. Check live connectivity | the main agent, once credentials are supplied | logon, subscription, first messages decoded, a `--dump` run |
| 7. Report | the main agent | a report of the decisions taken, the tests and their results, the open questions, and a pull request |

The skill stops after step 1 and does not continue until the user approves the
feed description.

## The feed description

The feed description is the interface between reading and writing. It is a
markdown file with fixed sections, so that the user can review it in one sitting
and the later steps can be generated from it.

1. **Venue and documents.** Each document with its version and date; which version
   applies where several are present.
2. **Transport.** Addresses, ports, protocols; A/B feeds; session and logon; heartbeats;
   throttles.
3. **Framing.** Packet and message headers; length fields (and whether they include
   themselves); endianness; alignment; batching of messages in a packet.
4. **Message catalogue.** One table per message, in the form already used by the m2
   field tables: field, offset, length, type, meaning. Offsets are stated as 0-based.
5. **Sequencing and recovery.** Sequence-number scope (per channel, per instrument,
   per session); gap detection; the recovery mechanism (snapshot channel, request
   and retransmission, Glimpse-style snapshot, REST snapshot); the rule that aligns
   a snapshot with the incremental stream; channel resets.
6. **Semantics.** For market data: MBO or price level; depth limit; how each update
   applies; queue-priority rules; how trades appear; implied prices; trading states.
   For post-trade: report types, amendments, cancellations and busts; identifiers;
   replay on reconnect.
7. **Mapping to Kaspar.** For each venue message, the Kaspar records or messages it
   produces.
8. **Instruments.** Where instrument definitions come from; symbology; tick size,
   price and quantity scaling per instrument.
9. **Ambiguities.** Every point where the specification is unclear or contradicts
   itself, with the agent's reading and its alternatives. Each must be resolved by
   the user or by sample data.

## Pitfalls the agent must check for

The skill carries a checklist of the errors that have caused problems in practice,
and the agent records in the feed description how each one applies to the venue.
The full list is in `.claude/skills/build-feed-handler/pitfalls.md`. Its sections:

- **Reading the specification:** versions and errata; several specification files
  for one feed; tables split across PDF pages; offsets that are 1-based; lengths that
  include or exclude the length field; reserved and padding fields; enumerations
  defined in a different section from their fields.
- **Framing and encoding:** endianness; signed or unsigned; fixed-point prices with
  per-instrument decimals; null values; strings padded with spaces or zeros.
- **Sequencing and recovery:** the scope of sequence numbers; the rule that aligns a
  snapshot with the buffered incremental stream (the Binance straddle rule); state
  that must be cleared on a channel reset (the stale order-ID map fixed in #122);
  recovery paths that only run on a bad day and must be exercised by injection.
- **Book semantics:** price-level insert, change and delete with level shifting;
  depth-limited books; queue priority on modify; implied prices; trades that are or
  are not also reported as book deltas (the double count `Mbp2Mbo` avoids); the side
  a trade reports, which differs between venues (Coinbase reports the resting side,
  Hyperliquid the aggressor); trading states and auctions.
- **Prices and quantities:** price versus yield (US Treasuries trade in either);
  quantity multipliers (the notional of one unit, published per book); sentinel
  values (a decimals field of -1 meaning *ignore*).
- **Undocumented behaviour:** options that change update rates (Hyperliquid's
  `fast` subscription); initial messages that replay history (Hyperliquid's trades,
  Coinbase's trade snapshot); a snapshot that is the whole book rather than its top.
- **Post-trade:** amendments and busts; duplicate reports on reconnect (`PossDupFlag`);
  replay from the start of day; acknowledgements the venue requires; FIX 4.4 against
  FIX 5.0 SP2 with FIXT transport; custom tags in the venue's dictionary.

## Verification

A handler is accepted on evidence, in this order:

1. Unit tests built from the specification's worked examples and from sample
   messages.
2. Replay of captures with invariants: no crossed book in continuous trading,
   contiguous sequence numbers, no order left behind after its delete.
3. Gap, duplicate and reset injection during replay.
4. Comparison with a reference: the venue's decoder, vendor data, or REST snapshots.
   This is the only check that catches errors which produce a plausible but wrong
   book, such as a wrong priority rule or a level shift that is off by one.
5. The live connectivity check.

The private m2 field tables for Fenics UST and Dealerweb, extracted by hand from the
venues' PDFs, serve as answer keys: the agent's extraction from the same PDFs is
compared field by field with them before the agent is used on a venue without an
answer key.

## Implementation as a Claude Code skill

```
.claude/skills/build-feed-handler/
  SKILL.md            the workflow, its stopping point and the rules
  pitfalls.md         the checklist
  feed_template.md    the feed description, with its fixed sections
```

The skill runs in Claude Code in the user's checkout. It uses subagents for
extraction (one per part of a long specification), generation and testing, and
the main agent for review, the live check and the report. PDFs are read directly,
up to 20 pages per request; tables are cross-checked against `pdftotext -layout`
output, because tables split across pages are a frequent source of extraction
errors.

### The Claude Agent SDK

The Claude Agent SDK is a Python and TypeScript library that provides the agent loop
behind Claude Code (tools, permissions, subagents, MCP servers and hooks) to
programs. It is used to build an agent as a stand-alone application rather than as
a skill inside an interactive Claude Code session. A skill in this repository is
sufficient while the agent is used by kaspar-hft developers in their own checkout;
the SDK becomes relevant if the agent is offered as a service, for example to
build handlers for client firms without a Claude Code session.

## Plan

| Phase | Work | Outcome |
|---|---|---|
| 0 | The feed-handler contract written down as one interface for each kind; a normalized trade-capture message for post-trade; the shared test harness (invariants, replay, injection, comparison); the skill, the checklist and the template | one target per handler kind |
| 1 | Extraction measured against the answer keys: Fenics UST market data and Dealerweb ITCH | field-level accuracy of extraction, and the checklist items the agent missed |
| 2 | Crypto venues with public data and a REST reference: OKX, Bybit, Kraken, Deribit, one held out as a blind test | time to a working handler, discrepancies against snapshots, edits needed |
| 3 | Post-trade FIX handlers from the venues' dictionaries: Dealerweb (FIX 4.4), Fenics (FIX 4.4), ICAP (FIX 5.0 SP2) | trade capture from three venues |
| 4 | Binary multicast with recovery on a venue without an existing handler (Nasdaq TotalView-ITCH, whose sample files are public; then the venue in the current client request) | the full workflow on a new venue |

No specification documents for ICAP are in the m2 repository; only its handler code
is. The ICAP post-trade dictionary or specification must be obtained before phase 3
covers it.
