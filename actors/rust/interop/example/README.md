# Hybrid C++/Rust interop — worked example + benchmark

A single process containing **both** a Rust actor and a **real C++ Kaspar actor**, where the Rust
side calls the C++ actor over the C-ABI FFI bridge — location-transparently. It also times that
cross-language call against a same-language (Rust→Rust) baseline.

This is the runnable counterpart to [`../README.md`](../README.md) (which explains the design).

## What it does

- The **C++ side** ([`cpp/hybrid_cpp.cpp`](cpp/hybrid_cpp.cpp)) creates a C++ `Manager` and an actor
  `cpp_pong` that handles the generated `msg::Ping`, registers it by name, and calls
  `cpp_actor_init()` so the bridge can find it.
- The **Rust side** ([`src/main.rs`](src/main.rs)) installs the generated dispatch
  (`generated::register()`), then `Manager::get_ref("cpp_pong", …)` resolves the C++ actor as an
  `ActorRef::Cpp` and `fast_send`s to it in a loop.

One `fast_send` crosses the boundary like this:

```
Rust: cpp.fast_send(&Ping)  ->  match id 400  ->  Ping::to_c()  ->  cpp_actor_fast_send(name, id, &CPing)
   (C ABI)  ->  C++: get_actor_by_name("cpp_pong")  ->  Ping::from_c()  ->  target.fast_send(&msg::Ping)  ->  handler
```

The message set comes from the one schema, [`../messages/interop_messages.h`](../messages/interop_messages.h);
the marshalling and both dispatch tables are generated by
[`../codegen/generate.py`](../codegen/generate.py).

## Build & run

Prerequisites: a C++20 compiler and the framework's deps — Boost, ZeroMQ, Crypto++ (on macOS:
`brew install boost zeromq cppzmq cryptopp`).

```bash
# 1. Build the C++ actor framework (produces actors/cpp/libactors.a)
cd ../../../cpp && make opt && cd -

# 2. Compile the C++ side of this example (the generated bridge + the C++ actor)
bash cpp/build_cpp.sh

# 3. Build and run (cargo links the C++ objects + libactors.a via build.rs)
cargo run --release
```

On Linux, point the library dirs at your install: `BOOST_LIB_DIR=… ZMQ_LIB_DIR=… CRYPTOPP_LIB_DIR=…
cargo run --release` (and `BOOST_INC_DIR=… bash cpp/build_cpp.sh`).

## What it measures

`fast_send` with no reply, across every sender/receiver combination of C++ and Rust actors in one
process. Representative (Apple Silicon, single thread, release, ns/call):

```
                    ->  Rust receiver       ->  C++ receiver
  Rust sender          ~15  (same lang)       ~70  (over FFI)
  C++  sender          ~46  (over FFI)        ~13  (same lang)
```

Same-language dispatch is ~13–15 ns. Crossing the boundary adds the marshalling (`to_c`/`from_c`
copies), the `extern "C"` call, the per-call name lookup, and the receiving-side dispatch. The two FFI
directions are not symmetric: Rust→C++ (~70 ns) pays for the C++ `get_actor_by_name` (a `std::string`
build + lookup + `ActorRef` return) each call, while C++→Rust (~46 ns) goes through the Rust inbound
resolver + `catch_unwind` guard. A latency-sensitive caller caches the resolved reference (this
example holds the `ActorRef::Cpp` and reuses it) rather than resolving by name every time.

Note: cross-boundary **replies** are not wired yet (a cross-language `fast_send` returns nothing), so
this measures one-way calls.
